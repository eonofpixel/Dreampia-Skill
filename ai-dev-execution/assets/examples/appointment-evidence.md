# 예약 예제 실행 증거와 인수인계

이 문서는 실행 기록의 형식을 보여 주는 **미실행 예제**다. 기능을 구현하거나 테스트·배포한 적이 없으므로 아래 결과는 모두 **NOT_RUN**이다. [예약 명세](appointment-spec.md)의 요구사항과 [테스트 계획](appointment-tasks-tests.md)의 기대값은 계획이며 관찰 결과가 아니다. 문서 작성이나 링크 검사가 통과해도 앱의 기능 검증이 통과한 것은 아니다.

## 현재 작업 맥락

| 항목 | 현재 사실 |
| --- | --- |
| 프로젝트 | 가상 상담 예약 예제 |
| 실행 모드 | 문서만 |
| 문서·작업 상태 | draft |
| 실제 저장소·코드 기준점 | 없음. 앱 저장소·커밋 생성 안 함 |
| 실행 환경·DB·도구 버전 | 미선정 |
| 앱·배포 URL | 없음. 생성·검증하지 않음 |
| 실제 실행 명령 | 없음. 테스트 runner·스크립트 미구현 |
| 실제 실행 시각 | 없음. 명세의 2030년 시각은 fixture일 뿐 실행 시각 아님 |
| 로그·스크린샷·DB 결과 파일 | 없음. 증거 파일을 만들지 않음 |
| 비밀값·실사용자 데이터 | 없음 |

## 단계별 기록

같은 TEST를 Red, Green, Refactor에서 다시 실행할 수 있지만 테스트 정의는 [테스트 계획](appointment-tasks-tests.md)에 한 번만 둔다. 실제 실행 시 아래 행에 명령·환경·코드 기준점·시각·로그 위치를 추가한다. 실행하지 않은 출력이나 FAIL을 지어내지 않는다.

| 단계 | 관련 작업·검증 참조 | 예상되는 확인 | 관찰 결과 | 결과·이유 |
| --- | --- | --- | --- | --- |
| Red | TASK-001; TEST-001, TEST-007, TEST-010의 관련 사례 | 구현 전 요구 행동 때문에 실패 | 없음 | NOT_RUN. 테스트·앱 미구현 |
| Green | TASK-001; 같은 관련 사례 | 목록·접근·시간·상태 검증 통과 | 없음 | NOT_RUN. 구현 및 실행 환경 없음 |
| Red | TASK-002; TEST-002~TEST-009 및 TEST-001 관련 사례 | 예약·경쟁·재시도·접근 행동의 미구현 실패 | 없음 | NOT_RUN. 테스트·앱 미구현 |
| Green | TASK-002; 같은 관련 사례 | 최소 구현이 계약과 DB 불변식 충족 | 없음 | NOT_RUN. 구현 및 실행 환경 없음 |
| Refactor·회귀 | TASK-001, TASK-002; 전체 테스트 참조 | 최종 코드의 계약 보존·전체 필수 검증 통과 | 없음 | NOT_RUN. 최종 코드 없음 |
| 최종 E2E | TEST-002 | 실제 UI → API → DB → 재조회 연결 확인 | 없음 | NOT_RUN. 앱 URL·실행 도구 없음 |

## 게이트 판정

| 게이트 | 상태 | 현재 판정과 남은 조건 |
| --- | --- | --- |
| G0 입력 확인 | draft | 가상 브리프만 있음. 실제 사용자·프로젝트 경로·실행 모드 확인 필요 |
| G1 실현 가능성·범위 | draft | 예제 범위와 설계안만 있음. 실제 환경·제약과 사용자 승인 필요 |
| G2 계약·테스트 준비 | draft | 계약·테스트 계획 있음. 실제 환경, 실행 가능한 테스트와 승인 범위 미확정 |
| G3 기능 검증 | blocked | 필수 기능 검증 전부 NOT_RUN. 통과 아님 |
| G4 릴리스 준비 | deferred | 배포가 예제 범위 밖. 운영 설정·보안·롤백·배포 권한 검토 안 함 |
| G5 출시 후 결과 | deferred | 실제 배포 없음. 관측 결과 없음 |

## 다음 실행자가 할 일

1. [시작 프롬프트](../prompts/start-project.md) 또는 [재개 프롬프트](../prompts/resume-project.md)에 실제 프로젝트명·경로·모드·환경을 넣는다. 저장소와 사용자 변경부터 검사한다.
2. 실제 인증·시간대·정원 정책을 확인하고 예제 가정을 승인된 요구사항으로 대체한다. 예제 ID는 프로젝트 내에서 유일하게 관리한다.
3. 격리 테스트 환경·스택·runner를 선정하고 승인 필요 작업을 구분한다. 설치, 자격증명·권한, 비용, 데이터 초기화·삭제, 공유, 배포의 실제 승인 없이 진행하지 않는다.
4. G2 준비 조건을 충족한 뒤 TASK-001부터 Red → Green → Refactor로 수행한다. TASK-002의 DB 동시성·멱등성 검증을 메모리 테스트로 대체하지 않는다.
5. 실제 명령·코드 기준점·시각·관찰·로그 위치와 함께 결과를 갱신한다. 모든 필수 검증이 통과한 뒤에만 해당 작업을 verified로 바꾼다. 과거 기록은 삭제하지 않고 새 실행을 추가한다.

실제 프로젝트의 실행 기록 예시는 다음 빈 필드로 시작한다. 값이 없으면 없음 또는 미정으로 적는다.

```text
관련 TASK / TEST ID:
단계: Red / Green / Refactor / E2E
코드 기준점과 미커밋 변경 식별:
실행 환경과 도구 버전:
실제로 실행한 명령:
실행 시작·종료 시각과 시간대:
기대 결과의 기준 문서·버전:
실제 관찰:
결과: PASS / FAIL / NOT_RUN
로그 또는 증거의 실제 위치:
확인하지 못한 경계와 이유:
다음 행동·담당·필요 승인:
```

## 멈춤 조건과 출시 이후

현재 문서만 작업은 이 기록으로 종료한다. 추가 구현·검증을 시작하려면 실제 실행 요청과 준비된 환경이 필요하다. 운영 배포나 정기 모니터링은 요청하지 않았으므로 만들지 않는다. 향후 배포가 승인되면 대상·성공 지표·롤백 조건·관찰 종료 조건을 먼저 정하고 그 범위에서 결과를 확인한다. 이 문서는 영구 권한을 부여하거나 호스트 안전 규칙을 대신하지 않는다.
