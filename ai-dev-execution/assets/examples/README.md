# 예약 서비스 미니 예제 읽기

정원 한 명인 상담 시간을 예약하는 가상 서비스로, 요구사항이 계약·작업·테스트·실행 증거에 어떻게 이어지는지 보여 준다. 앱이나 테스트 실행 결과를 제공하는 예제가 아니다. 사용자·시간·식별자는 모두 가상이며 기능 검증 기록은 전부 **NOT_RUN**이다. 이 예제의 문서·작업 상태는 별도 표기가 없으면 **draft**다. 실제 승인과 기능 검증은 아직 없다.

## 읽는 순서

1. [예약 명세](appointment-spec.md): 사용자 결과, 화면 상태, API·데이터 계약, 설계 결정
2. [작업과 테스트](appointment-tasks-tests.md): 수직 기능 단위 작업, 테스트 단일 정의, Red/Green/Refactor 계획
3. [증거 기록](appointment-evidence.md): 기대 결과와 미실행 상태, 게이트 판정, 다음 실행

이 파일까지 네 문서가 하나의 연결된 예제다. 실제 프로젝트에는 [원본 템플릿](../templates/00-project-brief.md)부터 [인수인계](../templates/10-progress-handoff.md)까지 사용한다. 예제의 작은 규모 때문에 문서를 합쳤을 뿐, 기준 정보의 소유권은 아래처럼 분리했다.

| 예제 기준 정보 | 예제 문서 | 실제 프로젝트의 원본 템플릿 |
| --- | --- | --- |
| 목표·요구사항·UX | appointment-spec | 00-project-brief, 01-prd, 02-ia-ux |
| 아키텍처·설계·계약·결정 | appointment-spec | 03-trd-architecture, 04-solution-design, 05-contracts-data, 09-decision-log |
| 작업·기대 검증 | appointment-tasks-tests | 07-backlog, 06-test-plan |
| 실제 실행·게이트·출시 제약 | appointment-evidence | 10-progress-handoff, 08-release-runbook |

## 한 줄로 추적하기

PRD-R003의 “동시에 예약해도 한 명만 성공” → API-002의 충돌 계약 → TASK-002의 원자적 예약 저장 → TEST-003의 동시 요청 Red → 같은 계약을 만족하는 Green 구현 → TEST-003 재실행과 TEST-002 E2E → 증거 기록. 모든 단계의 현재 실행 결과는 NOT_RUN이며, 화살표는 계획된 연결이다.

## 그대로 복사하면 안 되는 부분

- 예제는 취소·결제·알림·관리자·실제 고객 정보를 제외했다. 실제 서비스의 요구사항으로 승인받은 내용이 아니다.
- 시간은 고정된 2030년 fixture다. 실제 운영 날짜나 현재 시각으로 해석하지 않는다.
- 테스트 코드는 의사코드다. API 어댑터, DB fixture, 인증 fixture, E2E 도구가 구현되기 전에는 실행할 수 없다.
- API 계약은 명세이며 배포된 API가 아니다. 실행 URL, 저장소, 커밋, 로그 파일은 생성하지 않았다.
- 동시성 테스트는 실제 목표 DB에서 검증해야 한다. 메모리 배열이나 목 DB만으로는 데이터 불변식을 검증했다고 할 수 없다.
- 이 자료는 영구 실행 권한을 부여하지 않는다. 환경·자격증명·설치·비용·데이터 삭제·공유·배포의 실제 승인과 호스트 안전 규칙을 별도로 따른다.

다음 행동은 [시작 프롬프트](../prompts/start-project.md)로 환경과 범위를 확인한 뒤 예제를 프로젝트에 맞게 바꾸는 것이다. 문서만 모드에서는 여기까지의 명세·계획만 작성한다.
