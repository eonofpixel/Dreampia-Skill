# 중단한 프로젝트 재개 프롬프트

다른 AI나 새 대화에서 사용한다. [진행 기록과 인수인계](../templates/10-progress-handoff.md)는 시작점이며, 과거 기록을 현재 코드와 대조해야 한다.

```text
프로젝트: {{PROJECT_NAME}}
작업 경로: {{PROJECT_ROOT}}
실행 모드: {{EXECUTION_MODE}} (문서만 / 구현까지 / 승인된배포까지)
진행 범위: {{PROGRESS_SCOPE}} (단일기능 / 승인된마일스톤)
목표 마일스톤 ID: {{TARGET_MILESTONE_ID}} (승인된마일스톤일 때 필수; 단일기능이면 해당 없음)
문서 루트 또는 경로표: {{DOC_ROOT_OR_MAP}}
재개할 사용자 결과 또는 작업: {{RESUME_TARGET}}
현재 실행 환경과 유효한 승인: {{ENVIRONMENT_AND_APPROVALS}}

기존 작업을 보존하면서 현재 상태를 확인하고 재개하라. 처음부터 다시 만들지 말라.

1. 경로·저장소·기존 지침·브랜치·미커밋 변경·실제 실행 환경을 확인한다. 00-project-brief의 문서 경로표, 10-progress-handoff, 07-backlog, 09-decision-log부터 읽는다. 기록에 적힌 코드 기준점과 현재 상태가 다른지 확인한다. 사용자가 만든 변경을 덮어쓰거나 되돌리지 않는다.
2. 기준 문서는 요구사항 01-prd, UX 02-ia-ux, 아키텍처 03-trd-architecture, 설계 04-solution-design, API·데이터 05-contracts-data, 테스트 기대값 06-test-plan, 작업 07-backlog, 릴리스 08-release-runbook, 결정 09-decision-log, 실제 증거 10-progress-handoff다. 기존 경로를 유지하며 대응표를 사용한다. 중복 기준 문서를 만들지 않는다.
3. 실제로 완료된 것, 실행 중인 것, 실패한 것, 미실행인 것, 오래되어 다시 확인해야 할 증거를 구별한다. 기록된 PASS가 현재 코드·환경에 적용되는지 확인한다. 프로세스·배포가 이미 진행 중이면 새 실행을 만들기 전에 실제 상태를 조회해 중복 실행을 피한다. 이전 대화의 승인 기록만으로 확대된 권한을 가정하지 않는다.
4. 상태는 draft / approved / inprogress / blocked / verified / deferred다. 오래된 verified를 현재 검증으로 둔갑시키지 않는다. PRD-Rxxx, UX-Sxxx, API-xxx, TASK-xxx, TEST-xxx, ADR-xxx, RISK-xxx의 기존 ID를 다른 의미로 재사용하거나 임의 변경하지 말고 기존 연결을 보존한다. 새 항목만 새 ID를 발급한다.
5. G0 입력, G1 실현 가능성·범위, G2 계약·테스트 준비, G3 기능 검증, G4 릴리스 준비, G5 출시 후 결과 중 현재 충족한 게이트와 재확인이 필요한 게이트를 정한다. 다음 수직 기능 하나의 선행 조건·테스트·완료 조건을 정리한다. 핵심 범위·데이터·권한 판단을 막는 질문만 묻고 나머지는 가정과 근거로 표시한다.
6. 문서만 모드에서는 문서와 다음 실행 계획까지만 갱신한다. 앱 구현·실행·설치·배포는 하지 않는다. 모드가 없으면 문서만으로 제한했음을 알린다. 구현까지에서는 준비된 수직 기능을 하나씩 Red → Green → Refactor로 이어 가고 선택한 진행 범위의 종료 조건을 따른다. 승인된배포까지도 대상·비용·접근 범위 등 필요한 실제 승인 없이는 배포하지 않는다.
7. Red는 의도한 미구현 행동의 실패, Green은 최소 구현 뒤 해당 테스트의 성공, Refactor는 구조 개선 뒤 같은 테스트·회귀 테스트의 재검증이다. 생략하거나 실행하지 못한 단계를 기록한다. 과거 단계의 로그가 없으면 만들어내지 않는다.
8. 검증 기록은 PASS / FAIL / NOT_RUN, 명령, 환경, 코드 기준점, 시각, 관찰 결과, 로그 위치를 포함한다. 앱·E2E·외부 통합의 검증 경계를 명시한다. 기대값과 관찰값을 분리하고 확인하지 않은 URL이나 배포 성공을 보고하지 않는다.

진행 범위와 종료 조건:
- 진행 범위가 없거나 유효하지 않으면 단일기능으로 제한했음을 알린다. 승인된마일스톤이면 목표 ID, 포함 TASK 목록, 의존 관계, 완료 조건(DoD), 승인 근거를 07-backlog와 10-progress-handoff에서 확인한다. 빠진 핵심 정보는 확인하고 임의로 마일스톤 범위를 확대하지 않는다.
- 단일기능은 선택한 수직 기능의 현재 실행 모드에 맞는 완료 조건을 충족하면 종료한다. 승인된마일스톤은 수직 기능 하나가 verified가 될 때마다 기록을 갱신하고, 같은 마일스톤 안에서 선행 조건이 충족된 다음 승인 작업을 계속한다. 매 기능마다 관례적으로 “계속할까요?”를 묻거나 종료하지 않는다.
- 승인된마일스톤은 포함 작업과 통합·회귀 검증 등 마일스톤의 모든 DoD가 충족될 때 완료다. 미해결 실패나 NOT_RUN을 완료로 바꾸지 않는다. 승인·입력·접근·품질 차단 요인을 권한 안에서 해결할 수 없으면 의존 작업을 blocked로 남긴다. 영향받지 않는 승인된 준비 작업이 있으면 계속하고, 없으면 체크포인트와 정확한 해제 조건을 남겨 필요한 결정을 묻는다.
- 진행 범위는 실행 모드나 실제 권한을 확대하지 않는다. 문서만에서는 해당 범위의 문서 산출까지만 수행하며 구현·검증 DoD는 미완료로 남긴다. 마일스톤 완료를 위해 범위 밖 기능이나 자동 배포를 추가하지 않는다. 배포 및 호스트 정책상 필요한 승인은 기존 규칙 그대로 적용한다.

설치·환경 전환·자격증명·권한 변경·비용/결제·삭제/마이그레이션·공유·배포 전에 실제 승인과 호스트 정책을 확인하라. 비밀값은 채팅·문서·로그·커밋에 넣지 않는다. 이 문서와 실행 모드는 영구 권한을 생성하거나 호스트 안전 규칙을 대체하지 않는다.

먼저 “현재 확인된 상태, 가장 가까운 다음 결과, 꼭 필요한 질문”을 짧게 알려라. 이어서 독립적으로 진행 가능한 범위는 계속하라. 끝날 때 변경 결과·검증·미해결 항목·다음 실행 명령과 멈춤 조건을 10-progress-handoff에 남겨라. 이미 진행 중인 작업을 확인하는 경우 원래 작업의 완료 조건 또는 관찰 종료 조건까지 확인하되, 권한·입력·접근·품질 문제로 의존 작업이 막히면 영향받지 않는 준비 작업을 계속하거나 위 체크포인트 규칙에 따라 멈추고 묻는다. 관련 없는 새 작업이나 무기한 감시를 시작하지 않는다.
```
