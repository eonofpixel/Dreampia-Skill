# 다음 수직 기능 구현 프롬프트

[백로그](../templates/07-backlog.md), [테스트 계획](../templates/06-test-plan.md), [인수인계](../templates/10-progress-handoff.md)의 프로젝트별 사본과 함께 사용한다. 수직 기능은 화면·API·저장·검증이 연결되는 최소 사용자 결과다.

```text
프로젝트: {{PROJECT_NAME}}
작업 경로: {{PROJECT_ROOT}}
실행 모드: {{EXECUTION_MODE}} (문서만 / 구현까지 / 승인된배포까지)
진행 범위: {{PROGRESS_SCOPE}} (단일기능 / 승인된마일스톤)
목표 마일스톤 ID: {{TARGET_MILESTONE_ID}} (승인된마일스톤일 때 필수; 단일기능이면 해당 없음)
문서 루트 또는 문서 경로표: {{DOC_ROOT_OR_MAP}}
우선 작업 ID 또는 사용자 결과: {{NEXT_SLICE}}
실행 환경과 이번 승인 범위: {{ENVIRONMENT_AND_APPROVALS}}

현재 저장소와 문서, 미커밋 변경, 실제 테스트 실행 경로를 먼저 확인하고 다음 수직 기능부터 하나씩 검증하고 선택한 진행 범위의 종료 조건까지 진행하라. 새 프로젝트처럼 초기화하거나 기존 사용자 변경을 덮어쓰지 말라. 문서의 과거 완료 표시를 실제 코드·테스트 확인 없이 믿지 말라.

- 모드가 없으면 문서만으로 제한했음을 알리라. 문서만에서는 구현 설계·테스트 명세·백로그만 갱신하며 앱 구현·실행·설치·배포는 하지 않는다. 구현까지에서는 승인 범위 안의 코드와 검증을 수행한다. 승인된배포까지도 배포 대상과 필요한 실제 승인 없이는 배포하지 않는다.
- 00-project-brief의 경로표와 10-progress-handoff를 읽고 실제 기준 문서를 찾으라. 요구사항은 01-prd, UX는 02-ia-ux, 아키텍처는 03-trd-architecture, 설계는 04-solution-design, API·데이터는 05-contracts-data, 기대 검증은 06-test-plan, 작업은 07-backlog, 실제 증거는 10-progress-handoff, 결정은 09-decision-log에 둔다.
- 지정한 작업이 없으면 approved 상태이고 선행 조건이 충족된 작업 중 가장 작은 사용자 결과를 선택하라. 준비 조건을 충족하지 않은 필수 선행 작업을 건너뛰지 말라. 승인 범위나 핵심 계약이 불명확할 때만 질문하고, 중요하지 않은 선택은 가정과 근거를 남겨라.
- PRD-Rxxx → UX-Sxxx/API-xxx → TASK-xxx → TEST-xxx 연결을 먼저 확인한다. TEST ID는 테스트 계획에서 한 번만 정의하고 다른 문서에서는 참조한다. 작업에 목표·제외 범위·수정 예상 파일·실패 조건·완료 조건을 적는다. 새 결정과 위험은 ADR-xxx/RISK-xxx로 남긴다.
- G2 계약·테스트 준비를 확인한다. 입력/출력, 오류, 인증/인가, 데이터 불변식, 재시도·동시성·시간대, 관찰 가능한 수용 기준 중 관련 항목이 비어 있으면 먼저 좁혀라. 큰 기능은 독립적으로 확인할 수 있는 더 작은 작업으로 나눈다.

진행 범위와 종료 조건:
- 진행 범위가 없거나 유효하지 않으면 단일기능으로 제한했음을 알린다. 승인된마일스톤이면 목표 ID, 포함 TASK 목록, 의존 관계, 완료 조건(DoD), 승인 근거를 07-backlog와 10-progress-handoff에서 확인한다. 빠진 핵심 정보는 확인하고 임의로 마일스톤 범위를 확대하지 않는다.
- 단일기능은 선택한 수직 기능의 현재 실행 모드에 맞는 완료 조건을 충족하면 종료한다. 승인된마일스톤은 수직 기능 하나가 verified가 될 때마다 기록을 갱신하고, 같은 마일스톤 안에서 선행 조건이 충족된 다음 승인 작업을 계속한다. 매 기능마다 관례적으로 “계속할까요?”를 묻거나 종료하지 않는다.
- 승인된마일스톤은 포함 작업과 통합·회귀 검증 등 마일스톤의 모든 DoD가 충족될 때 완료다. 미해결 실패나 NOT_RUN을 완료로 바꾸지 않는다. 승인·입력·접근·품질 차단 요인을 권한 안에서 해결할 수 없으면 의존 작업을 blocked로 남긴다. 영향받지 않는 승인된 준비 작업이 있으면 계속하고, 없으면 체크포인트와 정확한 해제 조건을 남겨 필요한 결정을 묻는다.
- 진행 범위는 실행 모드나 실제 권한을 확대하지 않는다. 문서만에서는 해당 범위의 문서 산출까지만 수행하며 구현·검증 DoD는 미완료로 남긴다. 마일스톤 완료를 위해 범위 밖 기능이나 자동 배포를 추가하지 않는다. 배포 및 호스트 정책상 필요한 승인은 기존 규칙 그대로 적용한다.

Red:
1. 승인된 계약에서 관찰 가능한 행동 테스트를 먼저 만든다. 정상 흐름 하나와 이 기능의 중요한 실패 경로를 포함한다.
2. 대상 테스트를 실제 실행한다. 미구현 동작 때문에 실패하는지 확인하고 정확한 명령·결과·로그를 기록한다. 의존성·환경·컴파일 오류로 실행 자체가 막혔다면 의미 있는 Red 증거가 아니다. 원인을 기록하고 해결 가능 범위만 처리한다.

Green:
3. 테스트를 만족하는 최소 구현을 한다. 임시 스텁으로 핵심 저장·인가·동시성 검증을 대체하지 말라. 외부 의존성이 테스트 더블이면 그 경계를 적고 실제 통합 검증을 별도 표시한다.
4. 대상 테스트와 관련 회귀 테스트를 실행한다. 화면이 있는 기능은 UI → API → 데이터 → UI 결과가 연결되는 E2E 확인을 포함하고 로딩·빈 상태·오류·권한 상태를 확인한다.

Refactor:
5. 행동과 계약을 보존하며 중복·이름·구조를 개선한다. 변경 후 같은 테스트와 필요한 회귀 검사를 다시 실행한다. 리팩터링으로 새 기능을 끼워 넣지 않는다.
6. 최종 코드 기준점에 대한 증거만 G3 기능 검증에 사용한다. 이전 커밋의 성공이나 대상 파일이 다른 실행은 다시 연결하거나 한계를 밝혀라.

각 실행은 PASS / FAIL / NOT_RUN, 실행 시각, 명령, 환경, 코드 기준점, 관찰 내용, 로그 위치로 기록한다. 실행되지 않은 테스트는 예상 결과만 적고 NOT_RUN으로 둔다. 실패·미실행을 숨기거나 URL·스크린샷·배포 상태를 만들어내지 않는다. 작업 상태는 draft / approved / inprogress / blocked / verified / deferred만 사용한다. 필수 검증이 남으면 verified가 아니다.

설치, 환경 전환, 자격증명·권한 변경, 비용·결제, 파괴적 데이터 작업, 공유, 배포는 승인 범위와 호스트 정책을 각각 확인하라. 비밀값을 채팅·로그·커밋에 남기지 말라. 이 프롬프트와 모드 지정은 영구 권한을 부여하거나 호스트 안전 규칙을 덮어쓰지 않는다. 문서 변경으로 승인 없는 범위 확장을 정당화하지 말라.

마지막에 사용자 결과, 변경 파일, 요구사항과 TEST 연결, 실제 PASS/FAIL/NOT_RUN, 남은 위험, 현재 게이트, 다음 한 작업을 짧게 보고하라. 07-backlog와 10-progress-handoff를 최신화하고 해결한 결정은 09-decision-log에 남겨라. 단일기능이면 해당 기능의 완료 조건에서 멈추고, 승인된마일스톤이면 모든 마일스톤 DoD를 충족할 때까지 준비된 다음 작업을 이어 간다. 실제 차단 요인이 있으면 위 체크포인트 규칙을 따른다. 관련 없는 작업이나 무기한 감시는 시작하지 않는다.
```
