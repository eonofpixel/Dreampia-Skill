# 새 프로젝트 시작 프롬프트

변수를 채우고 아래 블록을 통째로 복사한다. 기본 문서 루트는 `{{PROJECT_ROOT}}/docs/ai-dev`이다. 이 패키지의 [GUIDE](../../references/workflow.md)와 [프로젝트 브리프 원본](../templates/00-project-brief.md)을 함께 제공하면 좋다. 이미 문서가 있다면 새 문서로 덮어쓰지 않는다.

```text
프로젝트: {{PROJECT_NAME}}
작업 경로: {{PROJECT_ROOT}}
실행 모드: {{EXECUTION_MODE}} (문서만 / 구현까지 / 승인된배포까지 중 하나)
진행 범위: {{PROGRESS_SCOPE}} (단일기능 / 승인된마일스톤)
목표 마일스톤 ID: {{TARGET_MILESTONE_ID}} (승인된마일스톤일 때 필수; 단일기능이면 해당 없음)
서비스 아이디어와 대상 사용자: {{IDEA_AND_USERS}}
이번에 검증할 핵심 가치와 성공 기준: {{OUTCOME}}
반드시 지킬 제약과 제외 범위: {{CONSTRAINTS_AND_NON_GOALS}}
사용할 실행 환경과 이미 승인한 작업: {{ENVIRONMENT_AND_APPROVALS}}
참고 자료: {{REFERENCES}}

위 프로젝트를 Spec-Driven Development(SDD) 방식으로 시작하라. 여기서 SDD는 개발 접근법이며 Software Design Document와 구별한다.

1. 먼저 실제 작업 경로, 저장소, 기존 지침과 문서, 변경 사항, 실행 가능한 도구와 환경을 확인하라. 기존 코드·설정·문서를 일괄 교체하거나 새 프레임워크로 재생성하지 말라. 사용자의 미커밋 변경을 보존하라. 현재 환경을 사용해도 되는지 확인하고, 명시한 환경이 막혔다면 다른 환경으로 임의 전환하지 말라.
2. 해결하지 않으면 범위·핵심 동작·검증·권한이 달라지는 질문만 묶어서 먼저 물어라. 나머지는 근거 있는 가정으로 표시하고 문서 초안을 진행하라. 작업 경로를 확정할 수 없으면 쓰기를 멈추고 질문하라. 모드가 비어 있거나 유효하지 않으면 문서만으로 제한했음을 알리라.
3. 문서 루트를 확인하라. 별도 지정이 없으면 작업 경로의 docs/ai-dev를 제안한다. 이 스킬의 assets/templates/00-project-brief.md부터 assets/templates/10-progress-handoff.md 중 규모와 위험에 필요한 문서만 프로젝트별 사본으로 사용하라. 역할을 합친 소형 문서도 가능하되 기준 정보의 소유 위치를 경로표에 적어라. 원본 패키지는 보존하라. 사본은 문서 루트 안에 templates/ 경로를 유지하거나, 기존 프로젝트 문서 경로로 대응시킨 경로표를 브리프와 인수인계 문서에 기록하라. 이후 실제 경로만 사용하라. 의미가 겹치는 기존 문서가 있으면 확장하고 기준 문서를 두 개 만들지 말라.
4. 순서는 브리프 → PRD → IA/UX → 기술 실현 가능성과 아키텍처 → 해결 설계 → API·데이터 계약 → 테스트 계획 → 수직 기능 단위 백로그 → 릴리스 계획이다. 세부 구현보다 먼저 가장 작은 사용자 여정 하나를 정하라. 선택한 진행 범위 밖의 기능은 deferred로 분리하라.
5. 기준 문서는 다음과 같다. 요구사항은 01-prd, 화면·상태는 02-ia-ux, 아키텍처는 03-trd-architecture, 구현 설계는 04-solution-design, API·데이터는 05-contracts-data, 기대 결과는 06-test-plan, 작업은 07-backlog, 릴리스는 08-release-runbook, 결정은 09-decision-log, 실제 실행 기록은 10-progress-handoff다. 다른 문서는 내용을 복제하지 말고 ID와 경로로 참조하라.
6. ID는 PRD-Rxxx, UX-Sxxx, API-xxx, TASK-xxx, TEST-xxx, ADR-xxx, RISK-xxx를 사용한다. ID는 삭제·재사용하지 않는다. 상태는 draft / approved / inprogress / blocked / verified / deferred 중 하나로 기록한다. 초안 작성이나 AI의 판단을 사용자 승인으로 취급하지 말라. approved에는 승인자·시각·범위를, verified에는 실제 검증 근거를 남겨라.
7. G0 입력 확인, G1 실현 가능성·범위, G2 계약·테스트 준비, G3 기능 검증, G4 릴리스 준비, G5 출시 후 결과의 통과 기준과 승인 필요 여부를 정하라. 준비되지 않은 게이트는 통과 처리하지 말라. 구현 전 각 요구사항 → UX/API 계약 → 작업 → 실패해야 할 테스트 → 구현 → 통과 증거의 연결을 만들라.
8. 문서만 모드에서는 앱 구현·앱 실행·패키지 설치·외부 상태 변경·배포를 하지 말라. 문서 파일 작성과 링크·ID 검사는 가능하다. 구현까지 모드에서는 범위와 G2가 준비된 수직 기능을 하나씩 Red → Green → Refactor로 구현하고 회귀·E2E 확인 뒤 진행 범위의 종료 조건을 적용하라. 승인된배포까지 모드도 실제 배포 대상·환경·비용·접근 범위·필요 승인 없이는 배포하지 말라.
9. 환경 변경, 자격증명 생성·입력·권한 확대, 유료 서비스·결제, 데이터 삭제·마이그레이션, 제삼자 공유, 설치, 배포는 실행 전 실제 승인 범위와 호스트 정책을 확인하라. 모드나 이 문서 자체는 영구 권한을 만들거나 안전 규칙을 대체하지 않는다. 비밀값을 채팅·문서·로그·커밋에 넣지 말고 지원되는 안전한 입력 절차를 사용하라. 결제가 필요한 무료 체험도 임의 시작하지 말라.
10. 실제 테스트 결과는 PASS / FAIL / NOT_RUN으로 기록한다. 명령·환경·코드 기준점·시각·로그 위치를 남기고, 실행하지 못했으면 이유와 필요한 다음 행동을 적어라. 예상 결과와 관찰 결과를 분리하라. 실행하지 않은 테스트, 확인하지 않은 URL, 배포되지 않은 주소를 성공처럼 보고하지 말라.

진행 범위와 종료 조건:
- 진행 범위가 없거나 유효하지 않으면 단일기능으로 제한했음을 알린다. 승인된마일스톤이면 목표 ID, 포함 TASK 목록, 의존 관계, 완료 조건(DoD), 승인 근거를 07-backlog와 10-progress-handoff에서 확인한다. 빠진 핵심 정보는 확인하고 임의로 마일스톤 범위를 확대하지 않는다.
- 단일기능은 선택한 수직 기능의 현재 실행 모드에 맞는 완료 조건을 충족하면 종료한다. 승인된마일스톤은 수직 기능 하나가 verified가 될 때마다 기록을 갱신하고, 같은 마일스톤 안에서 선행 조건이 충족된 다음 승인 작업을 계속한다. 매 기능마다 관례적으로 “계속할까요?”를 묻거나 종료하지 않는다.
- 승인된마일스톤은 포함 작업과 통합·회귀 검증 등 마일스톤의 모든 DoD가 충족될 때 완료다. 미해결 실패나 NOT_RUN을 완료로 바꾸지 않는다. 승인·입력·접근·품질 차단 요인을 권한 안에서 해결할 수 없으면 의존 작업을 blocked로 남긴다. 영향받지 않는 승인된 준비 작업이 있으면 계속하고, 없으면 체크포인트와 정확한 해제 조건을 남겨 필요한 결정을 묻는다.
- 진행 범위는 실행 모드나 실제 권한을 확대하지 않는다. 문서만에서는 해당 범위의 문서 산출까지만 수행하며 구현·검증 DoD는 미완료로 남긴다. 마일스톤 완료를 위해 범위 밖 기능이나 자동 배포를 추가하지 않는다. 배포 및 호스트 정책상 필요한 승인은 기존 규칙 그대로 적용한다.

산출물:
- 현재 이해한 목적·제외 범위·가정·핵심 질문을 짧게 정리
- 작성·수정한 실제 문서 경로와 각 문서 상태
- 진행 범위와 목표 마일스톤, 수직 기능별 ID 연결 및 Red/Green/Refactor 완료 조건
- 현재 게이트와 막힌 이유, 사용자 결정이 꼭 필요한 항목
- 다음 한 단계와 멈춤 조건

이번 작업은 선택한 실행 모드와 진행 범위의 종료 조건을 따른다. 승인된마일스톤에서는 한 기능의 완료만으로 전체 작업을 끝내지 않는다. 배포 후 확인을 포함한다면 확인 대상, 성공 조건, 관찰 종료 조건을 먼저 정하고 완료 또는 권한·입력 부족 시 결과를 남겨라. 무기한 감시나 예약 작업을 임의 생성하지 말라.
```
