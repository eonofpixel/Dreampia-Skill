# 드림피아 전문 역할 분담 및 인계 기준

visibility: internal_only

이 문서는 드림피아 개발 파이프라인에서 역할별 책임 분리, 실제 증거 수집, 단계별 인계(Handoff) 계약을 정의한다. 역할 문서는 모델 실행기나 운영 성능 인증이 아니다.

## 핵심 운영 원칙

| 원칙 | 드림피아 적용 기준 | 금지 사항 |
|---|---|---|
| 전문 역할/명확한 산출물 | 작업마다 책임·쓰기 범위·출력·수신자 명시 | 불필요한 전체 역할 동시 기동·과장된 표현 |
| 증거 수집 (Evidence Collection) | 외형은 직접 열람한 이미지, 동작은 assertion/trace, 저장은 새 프로세스 재조회 | 스크린샷만으로 제출/저장 완료 인증 |
| 사실 대조 (Reality Check) | 주장→실제 파일→최종 소스 해시 증거 대조, 미검증은 NOT_RUN | 근거 없는 자동 감점이나 임의 점수 부여 |
| 구조화된 인계 (Structured Handoff) | 동일 task ID, 승인 범위, 역할, 소유 경로, 수용기준, 해시 증거, 미해결 사항 | 체크박스만으로 PASS·배포 자동 진행 |
| 제한된 QA 루프 | 결함 재현→수정→영향 검증, 독립 리뷰 최대 2회 이후 문제/해제 조건 인계 | 무한 리뷰·자의적 범위 확장 |
| 단계별 게이트 | 승인된 마일스톤에 필요한 단계만 활성화 | 모든 과제에 불필요한 전사 출시 단계 강제 |

## 역할 계약 및 판타지 RPG 길드 직책 (기본 단일 실행, 필요한 독립 역할만)

- 발주자 (`Hero / 주인공 영웅`): 퀘스트 발주 및 최종 의사결정권자.
- `router` (`GuildMaster / 길드마스터`): 퀘스트 목표·위험도 분류 및 프로파일(`quick`/`team`/`controlled`/`cleanroom`) 작전 지휘.
- `planner` (`Sage / 세이지`): 대현자 · 원문/요구/승인대기 분리, acceptance ID 및 퀘스트 저널(SDD) 생성. 원문 사실을 고객 승인으로 바꾸지 않는다.
- `architect` (`Archmage / 아크메이지`): 대마법사 · API/데이터/신뢰 경계/폭발 반경/운영 제약. 구현자가 검증할 계약을 작성한다.
- `analyst` (`Alchemist / 알케미스트`): 연금술사 · `contaminated-zone` 바이너리/레거시 해부 및 `approved-spec` 클린룸 복원 원장 작성. 직접 프로덕션 코드를 구현하지 않는다.
- `executor` (`Paladin / 팔라딘`): 성기사 · 승인된 소유 경로(`owned_paths`)만 수정, 실제 실행 증거와 남은 범위를 인계한다 (`contaminated-zone` 접근 금지).
- `implementer` (`Knight / 나이트`): 기사 · 클린룸 명세 기반 핵심 구현 전담 (`contaminated-zone` 접근 금지).
- `design-critic` (`Archer / 아처`): 궁수 · UI 컴포넌트·반응형 레이아웃 고속 타격 및 시각 규격 비평.
- `ux-designer` (`Bard / 바드`): 음유시인 · 화면·상태·전환·한국어 가독성 정의. 렌더링 픽셀과 조작 검증을 분리한다.
- `reviewer` (`Inquisitor / 인퀴지터`): 심판관 · 별도 검토 주체가 실제 결함/재현/심각도/파일 위치를 반환. 없는 결함을 만들지 않는다.
- `verifier` (`Cleric / 클레릭`): 치유사 · 구현자의 요약을 인증으로 취급하지 않고 원본 로그/이미지/파일/원장 커버리지를 확인. 완료 판단에서는 보스 관문 사실 대조(reality-check) 역할을 겸한다.
- `privacy-guard` (`Guardian / 가디언`): 수호기사 · 이름/코드/토큰/학생 JSON/CSV·소규모 집계·반출 승인 및 클린룸 무오염 경계 점검. DOM 숨김과 응답 정제를 분리한다.
- `doc-writer`: 확인된 실행 결과·미완료·재개 방법으로 직원용/고객용 자료를 구분한다.

역할 이름(또는 길드 클래스 콜사인)이 다른 것이 다른 실행 주체의 독립 검토를 증명하지 않는다. 모델/도구/OS 샌드박스·유료 추론 권한을 새로 부여하지 않는다.

## 필수 인계 계약

[JSON 원본](../assets/internal/pipeline/handoff-contract.example.json)을 복사한다. `evidence`는 최종 프로젝트 내 파일의 SHA256을 계산해 채우고 확인 후 인계한다. 자리표시자 그대로 실행하면 실패해야 한다.

```bash
python3 -m harness.handoff_contract handoff.json --project /absolute/project
```

- 종료 0: 해당 범위의 수용기준 PASS, 파일/해시/성공 metadata 확인.
- 종료 1: 미실행/실패/blocked 기준 또는 미해결 사항으로 인계 완료 불가.
- 종료 2: 계약 누락·소유 경로 이탈·빈 성공 증거·변조된 해시·심볼릭 링크·모순된 실행 증거 등 유효성 오류.

선택 실행 검사기이며 기존 workflow/team CLI에 자동 연결된 정책 엔진이 아니다. 성공 metadata/해시는 실제 테스트 의미·시각 품질·실행 주체 신원·원격 실행 신뢰성을 인증하지 않는다. `verifier`가 증거의 내용과 소스 일치를 추가 확인해야 한다.

## 완료 전 사실 대조 (Reality Check)

1. 이번 승인 범위를 한 문장으로 고정한다. 로컬 앱/운영 서비스/독립 AI 자동화의 범위를 구분한다.
2. 요구마다 `implemented` / `deferred` / `approval-pending` 및 `PASS` / `FAIL` / `NOT_RUN`을 연결한다.
3. 수정 뒤 최종 소스로 build/unit/API/browser를 재실행한다. 교정 전 PASS는 현재 PASS가 아니다.
4. 스크린샷은 실제 열람한 수만 보고한다. 다른 실행 이미지의 해시가 같아 재사용했다면 그 근거를 기록한다.
5. 프로젝트 수정과 공통 스킬 반영을 구분한다. 공통 변경은 회귀·bundle manifest 갱신·설치본 해시 대조까지 확인한다.
6. 고객 공유/기관 승인/배포/재무 약정을 완료 게이트로 우회하지 않는다.
