# 선택적 제품 디자인과 UI 검증

사용자용 화면·흐름이 이번 범위일 때만 적용한다. API, 배치, CLI 또는 내부 실행 엔진만 요청됐다면 해당 경로를 검증하고 UI는 미적용으로 남긴다. 디자인만 요청되면 목업/설계까지, 구현이 요청되면 실제 UI 구현과 검증까지 진행한다. 이 절차는 프롬프트 정책이며 하네스가 자동 강제하거나 시각 품질을 인증하지 않는다.

## 플랫폼별 선택 로드

범위를 확인한 뒤 현재 표면에 필요한 자료만 읽는다: 브라우저는 [웹](design-web.md), 실제 앱 창은 [데스크톱](design-desktop.md), iOS/Android는 [모바일](design-mobile.md), 구현·검수 증거는 [검증](design-verification.md). hybrid는 관련 층만 조합한다. 스택/SDK를 확인하지 않고 플랫폼을 추측하지 않는다. UI 개선 요청이면 이미 작동하는 브랜드/기능을 보존하고 요청한 변화만 구현한다.

## 1. 제품 표면부터 맞추기

첫 구현 전에 기존 명세/짧은 작업 메모에 다음을 적는다. 별도 디자인 문서는 복잡하거나 공동 작업에 필요할 때만 만든다.

- 누가 어디서 여는 제품 화면인가: 웹 경로, 데스크톱 창, 모바일 화면 등 구체적인 진입점과 대상 환경.
- 핵심 흐름: 시작 → 사용자의 조작 → 연결될 기능/데이터 → 사용자에게 보이는 결과. 구현 책임과 제외 범위.
- 이번 DoD: 화면·흐름·필요한 상태 및 검증 환경. 엔진 성공과 UI 완료를 각각 판정할 조건.

화면에 대한 기대가 핵심적으로 모호하면 선택지가 결과를 어떻게 바꾸는지 짧게 질문한다. 명확한 요청에는 관례적인 재승인을 요구하지 않는다. 허용된 기존 디자인/프로젝트만 읽고 다른 사용자 프로젝트를 탐색하지 않는다.

## 2. 브랜드와 시각 방향

제공된 브랜드 문서·기존 실제 화면·컴포넌트·토큰·참조의 읽은 위치를 기록한다. 외부 참고는 연구 입력으로 취급하고 텍스트/코드/이미지를 재사용하기 전에 출처·버전·라이선스·권한을 확인한다. 못 읽은 참조를 봤다고 하지 않는다.

기존 체계가 있으면 유지하며 이번 변화만 설명한다. 없으면 대상 사용자와 실제 콘텐츠를 기준으로 간단한 방향을 직접 정한다. 제품에 맞는 정보 위계·밀도·레이아웃과 핵심 행동을 먼저 정하고, 색 역할·타이포 위계·간격·크기·경계/초점 등 필요한 토큰만 선택해 코드의 기존 변수/스타일에 반영한다. 특정 글꼴·장식·유행 팔레트·애니메이션을 모든 제품에 강제하지 않는다. 레퍼런스를 재현하라는 요청은 충실히 따르되 권리 없는 자산을 복제하지 않는다.

실제 콘텐츠로 방향을 검증한다: 한국어 제목·한글 입력기 조합·긴 이름/파일명·숫자·빈/다수 데이터, 지원 글자 확대·font fallback에서 위계/줄바꿈/조작을 확인한다. 임의 영어 lorem ipsum만으로 화면을 확정하지 않는다. 색·글자·간격·경계/초점 등 역할별 토큰을 기존 코드의 원본 한 곳에 연결하고 상태/테마가 요구되면 의미와 대비를 맞춘다. 고정 팔레트·새 토큰 파일·항목수·서체 변경은 의무가 아니다.

핵심 화면/좁은 대상 창에서 무엇이 우선인지와 조작→피드백을 짧게 정한다. 여러 시안·와이어프레임·새 토큰 파일은 결정에 필요할 때만 만든다. 문구는 실제 사용자가 하는 행동과 회복 방법을 설명한다.

## 3. 화면에서 실제 기능까지 구현

합의된 레이아웃과 토큰으로 기존 스택에 구현한다. 버튼·입력·탐색에 실제 의미와 상태 전이를 연결한다. mock 데이터/disabled 동작/연결되지 않은 부분은 개발 기록과 인계에서 표시하고 교체 조건을 정한다. 연결되지 않은 버튼을 연결됐다고 표시하거나 테스트 통과를 위해 제품 요구를 낮추지 않는다.

필요한 상태만 선택한다. 비동기 작업이면 로딩·중복 입력·실패·취소 지원 여부, 첫 사용/검색이면 빈 상태, 저장 작업이면 오류·입력 보존·재시도·재조회, 창 기반 UI면 지원 창 크기/스크롤을 다룬다. 키보드가 대상 입력이면 초점·레이블·순서·닫기/초점 복귀를 확인한다. 색상만으로 상태를 구별하지 않고 대상의 글자 크기·대비를 확인한다. 모션을 쓸 때만 감소 설정을 고려한다. 관련 없는 상태나 기기는 짧은 이유로 미적용 처리하고 일률적인 표를 생성하지 않는다.

## 4. 실제 화면과 조작을 검증

사용 가능한 브라우저·앱·테스트 러너로 제품의 진입점을 열고 합의한 대표 크기에서 실행 화면을 확인한다. 임의 앱/창을 사용자 제품으로 착각하지 말고 경로·창·환경을 기록한다.

- 시각: 화면 캡처/관찰에서 정보 위계·정렬·잘림·긴/빈 콘텐츠·문구·초점·선택한 상태를 확인한다. 스크린샷에는 대상 화면/상태/크기를 연결하고 비밀·개인정보를 제외한다.
- 동작: 핵심 사용자 조작을 실제 수행해 기대한 변화와 오류/회복을 관찰한다. 필요한 키보드·창 크기 검증을 수행한다.
- 연결: 사용자 결과를 실제 엔진/API/저장/재조회와 연결해 확인한다. mock으로 가능한 시각·동작 검증과 실제 연결 검증을 별도 판정한다.

[증거 검수](design-verification.md)에 따라 실제 관찰 범위만 판정한다. 스크린샷 하나로 조작·저장·권한을 PASS 처리하지 않는다. 코드/DOM/단위 테스트만 보고 시각 PASS를 쓰지 않는다. 도구가 없으면 할 수 있는 구현·정적 검토를 진행하되 시각/조작 등 못 한 검증은 NOT_RUN, 이유·해제 도구를 기록한다. 필수 항목을 확인하기 전에는 UI 기능 전체 완료를 선언하지 않는다. 별도 검토자가 없으면 자기 검토라고 적는다. 수정 후 변경 화면/흐름과 영향을 받은 검증부터 다시 확인한다.

## 5. 완료 주장과 증거의 수준

| 수준 | 필요한 관찰 | 그 증거로 주장할 수 없는 것 |
| --- | --- | --- |
| 목업/prototype | 정적 화면 또는 모의 데이터/동작, 확인한 범위 | 실제 엔진/데이터 연결, 제품 전체 완료 |
| 내부 런타임 PoC | 엔진 실행·입력·출력 등 실제 내부 결과 | 사용자가 기대한 제품 화면·조작 완료 |
| 연결된 UI 기능 | 실제 제품 화면에서 조작 → 실제 기능/데이터 → 화면 결과; 필요한 상태 PASS | 제외된 흐름·배포·전체 제품 인수 |
| 합의된 제품/마일스톤 완료 | 해당 범위의 모든 필수 인수/회귀/검증 통과 | 범위 밖 기능·실제 운영 배포·미측정 효과 |

수준은 일렬로 자동 승격되는 상태가 아니다. 관찰한 범위만 주장한다. 기존 증거 기록에 화면/진입점·상태·연결 방식(mock/실제)·크기·조작과 기대/관찰·판정·캡처/로그 위치를 필요한 만큼 붙인다. 별도 원장이나 새 JSON 스키마는 요구하지 않는다.

## 6. 보고된 사용 실패와 경계 예

2026-10-08 사용자로부터 전달된 game-ai 사례: 에뮬레이터 실행/입력 PoC는 검증됐으나 사용자가 기대한 LD플레이어·블루스택 같은 앱 UI 대신 Android 내부 화면 캡처만 받았다. 기대 제품 표면과 실제 검증 대상이 달라 사용자용 UI 완료 기준을 충족하지 못한 사례다. 이 스킬 변경에서 원 프로젝트를 읽거나 재실행하지 않았으므로 기술적 PoC 결과는 전달된 보고이며 독립 재검증 PASS가 아니다. 특정 상용 앱을 복제하라는 일반 규칙으로 해석하지 않는다.

예: 에뮬레이터 관리 UI라면 목록 → 선택 → 실행/입력 → 호스트 앱의 상태/결과가 인수 대상인지 먼저 정하고 엔진 PoC와 나눠 검증한다. 에뮬레이터 실행 CLI만 요청됐으면 exit/output/프로세스 정리 등 CLI DoD가 대상이며 데스크톱 UI를 추가하지 않는다.
