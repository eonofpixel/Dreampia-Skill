# 디자인 구현·검수의 실제 증거

UI 변경의 필요한 검증을 정할 때만 읽는다. 별도 문서/원장을 추가하기보다 기존 인수 조건·진행 기록에 아래 정보 중 관련된 것을 붙인다.

## 한 흐름의 관찰 묶음

화면/창/경로와 버전·환경 → 데이터/상태 → 크기/입력 조건 → 실제 조작 → 기대/관찰 → PASS/FAIL/NOT_RUN/미적용과 증거 위치를 연결한다. 실제 연결인지 mock인지와 캡처·로그의 신선도를 표시한다. 숨겨진 개인정보·키를 증거에 남기지 않는다. screenshot에는 해당 상태/크기를 명시하고 로그에는 결과/재조회 등을 연결한다.

표본은 요청과 위험에 맞춘다. 한국어/긴 제목·파일명·큰 숫자·빈/다수 데이터 등 실제로 레이아웃과 입력을 깨뜨릴 조건을 고른다. 공개/합성 fixture를 사용할 수 있지만 실제 소비 데이터·운영 계정을 무단 읽지 않는다. 글꼴 fallback·줄바꿈·테마·초점/대비·모션/창 크기 변경을 필요한 상태에서 확인한다.

## 서로 다른 주장

| 관찰 | 판정 가능한 범위 | 대체하지 못하는 검증 |
| --- | --- | --- |
| 소스/토큰/링크/정적 분석 | 코드/파일 계약·검토 후보 | 렌더링·실제 입력·사용성 |
| 빌드/단위/상태 테스트 | 해당 코드 동작 | 전체 제품 창·native gesture·시각 품질 |
| 화면 캡처/실제 관찰 | 그 화면·상태·크기의 시각 결과 | 클릭/키보드·저장·권한·스크린리더 동작 |
| 실제 조작/재조회 | 관찰한 흐름/연결·회복 | 다른 상태·기기·미실행 접근성·전체 인증 |
| 독립 사례 계획 검토 | 계약의 적용/모순/누락 | 실제 UI 품질 효과·소비 프로젝트 구현 |

키보드/스크린리더/대비/감소모션 등 항목은 각각 실행 여부를 기록한다. 이름/역할 확인만으로 스크린리더 조작 PASS를 만들지 않는다. 대비는 실제 전경/배경·크기·상태/테마를 계산/관찰하고 기준·예외를 표시한다. 선택한 조건만 통과해도 모든 접근성/모든기기 인증은 아니다.

## 제한된 검수와 수정

기존 기준 화면과 목표 흐름부터 확인한다. 여러 상태·크기를 한 검수 묶음으로 보되 반복 수가 품질 증거가 되지 않게 한다. 사용자에게 중요한 실패(실행/데이터/접근성)와 취향/장식 제안을 구별하고 관찰·위치·사용자 영향을 기록한다. 브랜드에 맞는 글꼴·카드·색·모션을 이름만 보고 결함으로 판단하지 않는다.

중요 결함을 범위 안에서 수정하고 바뀐 화면/흐름과 영향받는 조건부터 확인한다. 팀 계약의 최대2회 검토를 따르되 남은 필수 실패를 상한 때문에 PASS로 바꾸지 않는다. 검증 도구가 없으면 가능한 구현/정적 검토를 진행하고 화면/조작 등 부족한 항목은 NOT_RUN·해제 조건으로 남긴다. 과거 캡처를 현재 구현과 대조하지 못했다면 현재 PASS 증거로 쓰지 않는다.
