# 실행 상세 지침

필요한 절만 읽는다. 기존 v0.3.1의 실행 정책을 보존한 상세 참조다.

## 1. 시작과 실행 범위

1. 최신 요청에서 목적·대상·제외 범위·실행 모드·종료 조건을 파악한다. 명시된 자연어 요청도 유효하다. 별도 양식을 채우지 않았다는 이유로 이미 허용한 구현을 다시 승인받지 않는다.
2. 실제로 접근 가능한 프로젝트·지침·문서·브랜치·미커밋 변경·런타임·테스트 도구부터 확인한다. 기존 작업을 보존하고 새 프로젝트라는 이유로 초기화하거나 스택을 교체하지 않는다.
3. 모드를 정하고 사용자에게 짧게 밝힌다.
   - **문서만**: 명세·설계·계약·테스트 계획·백로그와 문서 자체 검증. 앱 구현·앱 실행·설치·외부 변경·배포는 하지 않는다.
   - **구현까지**: 승인된 기능의 코드·테스트·실제 검증. 운영 배포는 제외한다.
   - **승인된배포까지**: 구현 검증 후 승인된 정확한 대상·버전·공개 범위·비용·데이터 영향·복구 조건에 맞춰 배포하고 확인한다.
4. 요청에서 모드가 정말 불명확하면 문서만으로 시작한다고 알리고, 구현 등 의존 작업에 필요한 질문만 한다. 제품 결정·민감 데이터·비가역 영향·권한을 바꾸는 질문을 묶고, 되돌릴 수 있는 기술 선택은 근거를 남겨 진행한다.
5. 진행 범위는 **단일 기능** 또는 **승인된 마일스톤**이다. 명시된 목표·포함 작업·DoD를 기준으로 삼는다. 범위가 모호하면 가장 작은 의미 있는 기능을 제안하고 스스로 릴리스 전체로 확대하지 않는다.

파일·셸·브라우저·네트워크·지속 실행은 모델 이름이 아니라 호스트가 제공하는 기능이다. 없는 기능을 가정하지 않는다. 필요한 파일을 못 읽으면 첨부나 관련 본문을 요청한다. 도구가 없으면 제한을 알리고 가능한 문서·정적 검토를 진행하며 실행 검증은 `NOT_RUN`으로 남긴다. 지정된 환경이 막혔다고 다른 컴퓨터나 운영 계정으로 몰래 전환하지 않는다.

## 3. 문서 크기와 기준 정보

- **소형 3~4개(역할 분리가 필요한 경우; 낮은 위험 한 흐름은 §8 간편 한 파일 우선)**: 요구·UX / 설계·계약·테스트 / 작업·결정·진행·출시. 운영이 복잡하면 출시를 분리한다.
- **표준 7~10개**: 기본 8개는 브리프+PRD / UX / TRD+상세 설계 / 계약 / 테스트 / 백로그 / 런북 / 결정+인계다.
- **복합**: 11개 원본 역할과 필요한 기능별 모듈을 사용한다. 결제·민감정보·다중 테넌트·마이그레이션 같은 위험에 따라 확장한다.

문서 수는 목표가 아니다. 다음 작업이 소비할 내용까지만 구체화한다. 합치거나 이동할 때 브리프의 문서 지도에 역할별 실제 `경로#절`을 적고 링크를 갱신한다. 소형이어도 실제 위험 검증은 생략하지 않는다.

기준 정보는 한 곳이 소유한다: 요구·인수 조건은 PRD, 화면·상태는 UX, 시스템·비기능 목표는 TRD, 처리·불변식은 상세 설계, 정확한 형식은 계약·데이터, 기대 결과는 테스트 계획, 작업·의존성은 백로그, 출시·복구는 런북, 결정 근거는 결정 로그, 실제 결과는 진행·인계다. 다른 문서는 ID와 경로로 참조한다.

`PRD-R001 → UX-S001 / API-001 → TASK-001 → TEST-001 → 실제 증거 → 릴리스`를 연결하고 `ADR-001`, `RISK-001`을 보존한다. 기존 ID를 다른 의미로 재사용하지 않는다. 문서·작업 상태는 `draft / approved / inprogress / blocked / verified / deferred`, 검사 결과는 별도 `PASS / FAIL / NOT_RUN`이다. 승인 근거 없이 `approved`, 검증 근거 없이 `verified`로 바꾸지 않는다.

## 4. 명세에서 실행으로

1. 첫 사용자, 해결할 문제, 관찰 가능한 성공 기준, Must·Later·제외선을 정한다. 가정·미측정·미확인과 사실을 구분한다.
2. 정상·거부·경계·복구 인수 조건을 정의한다. UX의 loading·empty·error·권한·취소·재시도·접근성을 필요한 만큼 다룬다.
3. 중요한 연동·성능·모델 품질의 불확실성은 범위·시간·비용이 제한된 실험으로 확인한다. SDK·모델·요금 같은 변동 정보는 접근 가능한 공식 자료로 확인하고 출처·기준일을 남긴다.
4. 상태 전이·불변식·인증/객체 권한·API 스키마·시간/금액 단위·오류·멱등성·동시성·저장 제약을 작업 전에 맞춘다. 적용하지 않는 부분에는 이유를 남긴다.
5. 실제 요청 경로의 시작→처리→관찰 가능한 결과가 이어지는 작은 수직 기능으로 나눈다. 화면/API/저장이 범위면 해당 연결→재조회까지, 로컬 엔진은 입력→엔진→출력/상태까지, CSV CLI는 입력 파일→정리→출력 파일 재조회까지 검증한다. 없는 UI/API/저장 계층을 추가하지 않는다. 각 작업에 요구 ID·입출력·선행 작업·소유 파일·실행 범위·검증·시작/완료/중단/재개 조건을 둔다. 공통 계약과 파일 소유권이 안정된 독립 작업만 병렬화한다.
6. G0 입력 → G1 범위·실현 가능성 → G2 계약·테스트 준비 → 기능별 G3 검증 → G4 출시 준비 → 승인된 배포 → G5 결과 확인으로 진행한다. [게이트](quality-gates.md)는 증거 점검이며 모든 기술 단계의 수동 승인이 아니다.

## 5. 구현과 실제 검증

- **Red**: 핵심 결정적 동작·결함의 테스트를 먼저 작성하고 실제로 실행해 의도한 실패를 확인한다. 설치 실패나 문법 오류는 행동의 Red 증거가 아니다.
- **Green**: 범위 안의 최소 올바른 구현으로 해당 테스트와 영향받는 회귀 검사를 통과시킨다.
- **Refactor**: 외부 계약을 유지하며 구조를 개선하고 다시 실행한다. 통과를 위해 테스트를 삭제·완화하지 않는다.
- 계산·권한·파서·상태 전이·중복/경쟁·회귀 버그에 TDD를 우선한다. 탐색용 UI·실험은 prototype으로 구별하고 재사용 전 인수 기준과 검증을 갖춘다.
- 정적 검사·단위·계약·실제 백엔드 통합·브라우저/기기 E2E·화면/접근성·보안·성능·복구·비용 중 위험에 맞는 검증을 수행한다. UI가 없는 서비스는 API/CLI부터 영속 결과까지 실제 경로를 검증한다. 관련 없는 UI 검사는 이유와 함께 제외한다.
- 백엔드 저장·권한·경쟁/재조회가 요구된 기능이면 실제 경로를 확인한다. 로컬 처리/CLI는 해당 입출력·오류·보존/프로세스 상태를 검증하며 원격 백엔드를 의무로 추가하지 않는다. 모의 서버·스크린샷·컴파일만으로 전체 경로를 검증했다고 하지 않는다. 허가된 테스트 계정·격리 데이터·sandbox를 사용한다.
- 제품에 비결정적 AI 기능이 있을 때만 버전 고정 평가 세트·홀드아웃·rubric·치명 실패·사람 표본 검토·지연/비용 평가를 추가한다. AI로 개발한다는 이유만으로 AI 제품 평가를 요구하지 않는다.
- 검증마다 `TEST ID / 버전·커밋 / 시각·시간대 / 환경 / 실제 명령·절차 / 기대 / 관찰 / PASS·FAIL·NOT_RUN / 증거 위치`를 남긴다. 미실행 이유와 해제 조건을 쓴다. 과거 Red·로그·성능값·URL을 만들어내지 않는다.
- 테스트 통과와 제품 인수를 별도로 검토한다. 필수 검증이 `FAIL` 또는 `NOT_RUN`이면 해당 게이트·마일스톤을 완료 처리하지 않는다.

## 6. 연속 진행·변경·재개

단일 기능이면 그 기능 DoD까지 진행한다. 승인된 마일스톤이면 각 기능을 검증하고 기록한 뒤 같은 범위의 다음 준비 작업을 계속한다. 매 기능마다 관례적으로 “계속할까요?”라고 묻거나 끝내지 않는다. 마일스톤의 통합·회귀·인수 DoD도 충족해야 완료다.

실제 차단 요인은 권한 안에서 진단·수정·재검증한다. 해결에 필요한 승인·입력·접근이 없으면 의존 작업만 `blocked`로 두고 다른 승인된 준비 작업을 계속한다. 더 진행할 독립 작업이 없으면 정확한 차단·해제 조건·체크포인트를 남기고 질문한다. 사용자의 중단이나 목표 DoD 도달 시 끝낸다. 무관한 기능·자동 배포·무기한 감시로 범위를 늘리지 않는다.

요구 변경은 이유와 원본 ID를 기록하고 범위·UX·계약·데이터·작업·테스트·보안·비용·릴리스·복구 영향을 분석한다. 필요한 제품 결정을 받은 뒤 기준 문서부터 갱신하고 영향을 받은 작업과 PASS의 유효성을 재평가한다. 코드가 다르다는 이유만으로 요구를 자동 변경하지 않는다.

컨텍스트·크레딧·접근·실행 시간이 부족해지기 전에 브랜치·커밋·미커밋 변경·문서 버전·실행 중 프로세스·실패 재현·실제 검사 결과·남은 승인/예산·다음 한 작업을 인계한다. 재개 시 현재 환경과 기존 실행 상태를 대조해 중복 실행을 피한다. 과거 PASS를 현재 버전의 PASS로 복사하지 않는다. 지속 작업은 호스트가 지원하고 범위·관찰 근거·종료 조건이 정해진 경우에만 약속한다.

## 7. 권한과 최종 보고

실행 모드와 이 스킬은 권한을 만들지 않는다. 설치·유료 호출/클라우드 예산·인증/영구 접근·공유·삭제/마이그레이션·배포는 현재 사용자 승인과 호스트 정책을 따른다. 비밀번호·API 키·토큰·결제정보를 채팅이나 산출물에 요구·복제하지 말고 지원되는 안전한 공급 절차를 사용한다.

보고는 **완료 결과와 실제 경로 / 실제 검증과 미실행 범위 / 남은 위험·필요한 결정 / 다음 행동 또는 종료 조건**으로 짧게 한다. G4 출시 준비와 실제 배포 완료를 구분한다. 배포한 경우 버전·대상·smoke 결과를 확인하고 합의된 관찰 조건까지 평가한다. 증거 부족은 성공으로 바꾸지 않는다.

## 8. 간편 모드와 현재 명세 / 변경분

낮은 위험의 한 흐름이라면 **간편 모드**를 우선 적용한다. [간편 원본](../assets/templates/compact-project.md)의 현재 명세·작업/테스트·증거 세 절을 한 파일로 유지하고 필요할 때만 분리한다. 기존 3~4개 소형 문서가 이미 있으면 합치지 않아도 된다. 작업 1~3개, 요구 ID, 실패 인수 조건, 실제 검증 명령, 범위·중단 조건부터 작성한다. 문서 파일 수가 완료 조건이 되지 않게 한다. 인증·금전·민감정보·운영 변경 위험이 생기면 해당 계약과 검증을 확장한다.

현재 명세는 **지금 유효한 동작**의 단일 기준이다. 변경분은 이유·추가/수정/폐기 요구 ID·영향·결정 근거를 담는 별도 기록이다. [변경분 원본](../assets/templates/change-delta.md)을 필요할 때 사용한다. 변경분을 새 명세와 혼용하지 않는다. 승인된 변경을 현재 명세에 반영하고, 영향받은 작업·테스트·증거를 stale 또는 NOT_RUN으로 돌린다. 명세가 바뀌어도 과거 실패·결정·Red 증거는 이력으로 보존한다.

## 9. 연결 검사와 두 종류의 리뷰

요구 ID → 작업 ID → 테스트 ID → 실제 증거 경로를 검사한다(`python3 -m harness.team_cli sdd-check --project <root>` 또는 MCP `dreampia_sdd_check`). 존재하지 않는 ID/파일, 순환 의존성, 필수 요구의 작업 누락(Orphan Spec), 테스트 없는 완료, 현재 명세 해시(`spec_sha256`)와 다른 `STALE` PASS를 기계적으로 차단한다. 링크 존재는 의미가 맞다는 보장이 아니므로 각 테스트가 요구의 정상·거부·경계를 실제 관찰하는지도 검토한다.

구현 후 [리뷰 기준](review-and-evaluation.md)에 따라 계약·오류·권한·데이터·경쟁·재개·테스트 맹점을 검토하고 결함은 범위 안에서 수정·재검증한다. UI가 있으면 실행 화면의 대표 크기·로딩/빈/오류 상태·위계·정렬·문구·대비·초점·키보드 흐름을 별도로 확인한다. 화면을 보지 않았으면 시각적 품질 PASS를 쓰지 않는다. UI 없는 CLI는 시각적 검토를 미적용(이유 포함)으로 남긴다. 별도 검토자가 없으면 자기 검토임을 밝힌다.

## 10. 하네스 연동과 이식성

이 스킬은 모델/호스트에 이식 가능한 지침이다. 명령 실행, 상태 저장, 격리, 권한은 호스트나 별도 하네스가 제공한다. 특정 코딩 CLI·모델·유료 호출을 요구하지 않는다. [하네스 경계](harness-integration.md)를 연동할 때만 읽는다. 하네스 소프트웨어는 스킬 밖의 별도 산출물이며 전역 설치 없이 실행한다.

지침으로 요구하는 항목(명세의 의미, TDD 실패 이유, 제품 인수, 코드 리뷰, 실제 화면 품질, 사용자 승인)을 프로그램이 자동 보장한다고 말하지 않는다. 프로그램은 명시된 스키마·의존성·시도 제한·잠금·검증 종료 코드·소스 해시 등 구현된 검사만 강제한다. 모의 어댑터 PASS는 오케스트레이션 검사이며 AI의 코딩 성능이나 실제 외부 서비스 품질의 증거가 아니다.

스킬 적용/미적용 효과를 평가할 때 [평가 시나리오](../assets/evals/scenarios.json)를 사용한다. 동일 작업·초기 소스·도구·예산·모델을 고정하고 독립 실행의 원시 산출물·로그로 비교한다. 실행하지 않은 평가에는 NOT_RUN을 적고 수치를 만들지 않는다. [실행 예제 안내](harness-integration.md)의 작은 예약 규칙을 이용해 로컬 하네스 흐름을 먼저 확인한다.

하네스 0.2.0은 루트 런타임과 중첩 소스 경로를 구별하고 파일 내용·경로·권한·디렉터리 구조를 증거 해시에 포함한다. 명세 의미나 외부 입력 전체를 추론하지는 않는다. 손상 상태·계획 변경의 recovery_hold는 자동 구현 재실행으로 풀지 않는다. 먼저 격리 복구/검사만 재검증하고 외부 부작용 재실행이 필요한 정확한 작업만 명시적으로 허용한다. 과거 verified 복원과 현재 실제 PASS 생성을 구별한다.

선택 Codex 어댑터는 비용·범위가 허용된 세션에서만 opt-in한다. 무료 help/version과 합성 fixture 검사 결과를 실제 공급자 추론 성공으로 기록하지 않는다. 인증 우회·권한 우회 플래그나 자동 무한 재시도를 넣지 않는다. 고정 baseline/holdout runner는 평가 작업 공간 준비와 관찰 기록 집계만 수행하며 모델을 호출하지 않는다. NOT_RUN 결과에는 효과 점수를 만들지 않는다. 제품 버전·지원 OS·원격 CI 실행 여부·배포 라이선스 미선정을 보고와 구별해 기록한다.
