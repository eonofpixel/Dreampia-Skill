# 개발 실행 상세 워크플로

새 프로젝트의 규모·문서 역할·설계, 구현/TDD, 검증, 변경, 재개를 위한 조건별 참고 자료다. 현재 작업에 필요한 절만 읽는다. 스킬의 공통 실행 규칙은 [SKILL.md](../SKILL.md), 게이트 판정은 [quality-gates.md](quality-gates.md)에 있다.

## 찾아보기

- 구현: 7 수직 기능·TDD, 8 실제 검증

- 연속 진행·재개: 11 권한·협업·인계

## 1 운영 원칙

1. 문서는 다음 작업이 실제로 소비할 만큼만 쓴다. 여러 문서를 한 번에 채우는 것이 목표가 아니다.
2. 구현 전에 사용자 가치, 범위 경계, 관찰 가능한 인수 조건을 정한다. 새로운 발견은 문서와 테스트에 반영한다.
3. 기존 저장소, 설정, 데이터, 외부 연동을 먼저 읽는다. 신규 서비스라는 이유만으로 기존 내용을 덮어쓰지 않는다.
4. 화면만 완성하거나 모든 기반 계층을 먼저 쌓지 않는다. 사용자가 시작해서 결과를 확인하는 **세로 기능 조각**을 하나씩 완성한다.
5. 실패를 숨기기 위해 테스트를 삭제하거나 조건을 느슨하게 하지 않는다. 명세 오류라면 변경 이유와 새 기준을 승인받고 수정한다.
6. 실행하지 않은 검증은 `NOT_RUN`이다. 추정, 계획, 예시, 실제 결과를 분리한다.
7. 기능 통과와 제품 인수는 별개다. 테스트가 잘못된 요구를 정확히 구현했을 가능성도 검토한다.
8. 외부 비용, 운영 변경, 데이터 공유, 자격 증명은 별도 권한 경계다. 문서의 실행 모드만으로 권한이 생기지 않는다.
9. 모르는 것은 출처와 확인 방법을 남긴다. 재현 가능한 근거가 확보되면 가정을 대체한다.
10. 컨텍스트, 실행 시간, 접근 권한이 끝나기 전에 재개 가능한 상태를 남긴다. 실제로 지원하지 않는 상시 작업을 약속하지 않는다.

## 2 규모와 실행 모드 선택

### 규모

규모는 파일 수나 팀원 수보다 **위험과 결합도**로 정한다.

낮은 위험의 한 흐름은 간편 모드 한 파일을 우선하며 아래 문서 수는 더 많은 역할 분리가 필요한 경우의 가이드다.

| 규모 | 적합한 상황 | 유지 문서 | 반드시 남길 내용 |
| --- | --- | --- | --- |
| 소형 | 한 가지 사용자 흐름, 낮은 데이터 위험, 단순 연동 | 3개 또는 4개 | 요구·UX / 설계·계약·테스트 / 작업·결정·진행·출시. 출시가 복잡하면 운영 문서 분리 |
| 표준 | 인증, 영속 데이터, 몇 개의 사용자 흐름·외부 연동 | 7개에서 10개 권장 | 아래 기본 8개 통합안 사용 |
| 복합 | 결제, 민감정보, 다중 테넌트, 비가역 데이터 변경, 다수 서비스 | 11개 기본 템플릿과 필요한 기능별 명세 | 위협 모델, 마이그레이션, 운영, AI 평가 등 위험에 따라 확장 |

소형이라도 인증·권한·데이터 손실·실제 비용이 있으면 해당 검증은 생략하지 않는다. 처음에는 소형으로 시작하고 위험이 드러나면 문서를 분리한다.

**표준 8개 통합안**: 00+01 사업·요구, 02 IA·UX, 03+04 기술·상세 설계, 05 계약·데이터, 06 테스트, 07 백로그, 08 출시·운영, 09+10 결정·진행. 파일을 합쳐도 요구·계약·결정·증거의 소유 위치는 고정한다.

기본 템플릿 11개는 선택할 수 있는 원본이다. 새 프로젝트에 모두 빈 채로 복제할 필요는 없다. 유지할 실제 경로와 통합된 절을 프로젝트 브리프의 **문서 지도**에 적는다. 원본 패키지는 보관하고 프로젝트별 복사본을 사용한다. 이 패키지 안의 상대 링크를 그대로 쓰려면 폴더 구조를 유지한다. 경로를 바꾸면 링크와 프롬프트의 문서 지도를 함께 바꾼다.

### 실행 모드

- **문서만**: 탐색, 명세, 설계, 테스트 계획, 작업 분해, 검토. 앱 코드 작성·설치·배포·외부 변경은 하지 않는다. 예시 코드나 의사코드도 구현 완료로 표시하지 않는다.
- **구현까지**: 승인된 프로젝트 경계 안에서 코드와 테스트를 작성하고 실행한다. 필요한 설치, 외부 서비스 호출, 데이터 변경은 승인 범위를 별도 확인한다. 운영 배포는 포함하지 않는다.
- **승인된배포까지**: 구현 검증 후 특정 대상·버전·비용·데이터 영향·복구 방법이 승인된 배포만 수행한다. 이 모드를 선택한 사실만으로 모든 배포가 승인되지는 않는다.

프로토타입은 별도 표식 `prototype`을 붙인다. 검증할 가설, 제한 시간·비용, 가짜 연동, 폐기할 산출물, 재사용 시 다시 검증할 부분을 적는다. 프로토타입의 화면이나 임시 테스트를 운영 품질 근거로 삼지 않는다.

## 3 일곱 모듈과 단일 기준 문서

| 논리 모듈 | 기준 파일 | 책임 |
| --- | --- | --- |
| 목적과 제품 요구 | 00 브리프, 01 PRD | 대상 사용자, 해결할 문제, 성공 지표, 포함·제외 범위, 인수 조건 |
| 사용자 경험 | 02 IA와 UX | 화면 구조, 상태, 이동, 접근성, 오류와 회복 |
| 기술 방향 | 03 TRD와 아키텍처 | 환경, 기술 선택, 시스템 경계, 비기능 요구, 운영 제약 |
| 기능 상세 설계 | 04 상세 설계 | 기능별 처리 순서, 상태 전이, 불변식, 구현 대안 |
| 계약과 데이터 | 05 계약과 데이터 | API·이벤트·스키마·권한·시간·오류·호환성의 정확한 정의 |
| 품질 검증 | 06 테스트 계획 | 테스트의 기대 결과, 방법, 환경, 인수 기준, AI 평가 기준 |
| 실행과 운영 | 07 백로그, 08 런북, 09 결정, 10 진행·인계 | 순서·소유권·배포·복구·변경 이유·실행 증거·재개 |

요구사항의 문장은 PRD에, 정확한 API 형식은 계약 문서에, 테스트의 기대값은 테스트 계획 또는 연결된 테스트 정의에 둔다. 다른 문서는 ID와 경로로 참조한다. 같은 사실을 여러 곳에 복사하면 변경 때 모순이 생기므로 필요한 요약에 원본 링크를 붙인다.

충돌을 발견하면 AI가 편한 버전을 고르지 않는다. 관련 작업을 잠시 막고 원본·최신 변경·승인 범위를 비교해 변경안을 제시한다. 승인된 결정이 기준 문서에 반영된 뒤 구현을 재개한다. 기존 코드가 요구와 다른 것은 발견 사실이지, 자동으로 명세가 바뀌었다는 뜻이 아니다.

### 식별자와 상태

- `PRD-R001`: 사용자 요구. 소유자, 출처, 상태, 인수 조건을 갖는다.
- `UX-S001`: 사용자에게 보이는 화면 또는 상태 묶음.
- `API-001`: API 또는 이벤트 계약. 구현 경로와 독립적으로 안정적인 ID를 쓴다.
- `TASK-001`: 독립적으로 결과를 검증할 작업.
- `TEST-001`: 구체적인 테스트 시나리오. 요구 ID와 기대 결과를 연결한다.
- `ADR-001`: 중요한 설계 결정과 대안·근거·재검토 조건.
- `RISK-001`: 위험, 영향, 가능성, 대응, 담당자, 확인 기한.

ID를 삭제 후 다른 의미로 재사용하지 않는다. 폐기된 내용은 `deferred` 및 폐기 이유·대체 ID를 남긴다. 문서와 작업 상태는 `draft`, `approved`, `inprogress`, `blocked`, `verified`, `deferred`를 쓴다. `approved`는 지정한 결정권자의 승인 또는 명시적 위임 근거가 있다는 뜻이다. `verified`는 해당 범위의 근거가 확인됐다는 뜻이며 제품 전체 출시를 뜻하지 않는다. 검사 결과는 별도 열에 `PASS`, `FAIL`, `NOT_RUN`으로 기록한다. `NOT_RUN`에는 이유와 해제 조건을 쓴다.

추적 연결은 **요구 → UX·계약·설계 → 작업 → 테스트 → 실제 증거 → 릴리스**로 유지한다. 하나의 요구가 여러 테스트로 이어지는 것은 정상이다. 연결이 없는 작업은 왜 필요한지 먼저 확인한다.

## 4 시작과 탐색

### G0를 위한 입력 정리

[프로젝트 브리프](../assets/templates/00-project-brief.md)에 이름, 목적, 사용자, 실행 모드, 규모, 예산, 결정권자, 작업 환경, 배포 후보, 금지 범위를 적는다. “알아서 전부” 대신 파일 수정·설치·외부 호출·배포 범위를 구체적으로 나눈다.

기존 환경을 읽기 전엔 스택을 확정하지 않는다. 저장소 경로와 브랜치, 작업 중인 변경, 기존 지침, 빌드·테스트 명령, 버전·잠금 파일, 라이선스, CI, 연결 서비스, 데이터 존재 여부를 확인한다. 사용자의 미커밋 작업을 되돌리거나 새 프로젝트 초기화로 덮어쓰지 않는다. 비밀 값은 읽거나 요약해 문서에 복제하지 않고 변수 이름과 안전한 공급 방법만 적는다.

실행할 컴퓨터나 클라우드 환경과 실제 배포할 대상은 구분한다. 연결 여부, 필요한 런타임, 네트워크, 테스트 데이터, 서비스 접근을 확인하고 확인일을 기록한다. 선택한 환경이 없으면 의존 작업은 `blocked`로 두고, 가능한 문서 작성·정적 검토·테스트 설계를 계속한다. 몰래 다른 컴퓨터나 운영 계정으로 바꾸지 않는다.

### 중요한 질문과 되돌릴 수 있는 선택

제품의 대상, 금전·민감정보 영향, 범위·권한·법적 제약, 공개 여부가 불명확하면 질문한다. 질문에는 **추천안, 대안, 각각의 영향, 결정이 필요한 시점**을 붙인다. 사용자의 선택이 필요한 사안을 기술 판단으로 대신하지 않는다.

폴더명, 내부 함수 분리처럼 범위 안의 되돌릴 수 있는 기술 선택은 합리적인 기본값과 이유를 적고 진행한다. 모든 선택을 질문으로 돌리지 않는다. 미응답은 승인으로 처리하지 않는다. 의존하지 않는 작업은 별도로 계속한다.

## 5 제품 명세와 불확실성 제거

[PRD](../assets/templates/01-prd.md)에는 누가 어떤 상황에서 무엇을 얻어야 하는지 쓴다. “빠르다”, “직관적이다”, “완벽하다”를 측정 가능한 기준으로 바꾼다. 성공 지표에는 기준값의 출처, 목표, 측정 이벤트와 분모, 시간 창, 담당자, 개인정보 영향을 함께 둔다. 기준값을 모르면 `미측정`으로 쓴다.

첫 릴리스 범위에는 Must, 후속 범위에는 Later를 붙이고 **제외선**을 명시한다. 예를 들어 예약 생성이 범위라면 결제·취소 수수료·추천·다중 자원 예약이 포함되는지 각각 결정한다. 빠진 요구를 AI가 편의 기능으로 확대하지 않는다.

요구마다 정상·거부·경계·복구의 인수 조건을 적는다. Given/When/Then 또는 조건/행동/관찰 결과로 표현하고, 테스트 없이도 다른 사람이 합격 여부를 판단할 수 있게 한다.

### 기술 실험

외부 API의 실제 지원, 브라우저 제한, 실시간 지연, 모델 품질, 마이그레이션 가능성처럼 근거가 부족한 사항은 구현 약속 전에 작은 실험으로 확인한다.

실험에는 질문, 가설, 대상 환경, 허용 비용·시간, 측정 방법, 성공·실패 기준, 폐기할 코드, 결정에 사용할 근거를 적는다. 결과는 참·거짓뿐 아니라 `불충분`일 수 있다. 실패했으면 범위를 줄이거나 대안을 선택하거나 멈춘다. 성공처럼 보이게 목표를 낮추지 않는다. 실험이 끝나도 테스트·권한·배포 게이트는 그대로 적용된다.

의존 서비스는 담당자·이용 조건·요금·제한·대체안·검증일을 적는다. 모델·SDK·요금·약관처럼 바뀌기 쉬운 정보는 해당 공식 문서로 최신성을 확인한다. 다른 프로젝트의 수치를 이번 프로젝트의 사실로 가져오지 않는다.

## 6 UX와 기술 계약

### IA와 UX

[IA와 UX](../assets/templates/02-ia-ux.md)는 페이지 목록만 담지 않는다. 시작점, 핵심 행동, 완료 결과, 되돌아가기, 새로고침·직접 링크·세션 만료를 정의한다. 각 흐름의 `loading`, `empty`, `success`, `validation_error`, `permission_denied`, `offline`, `partial_failure` 등 적용되는 상태를 정하고 불필요한 상태는 이유와 함께 제외한다.

접근성은 키보드 조작, 초점 이동, 입력 레이블, 오류 연결, 읽기 순서, 대비, 확대·작은 화면, 스크린리더 알림을 고려한다. 최종 합격에는 실제 화면 크기와 도구·수동 검토 근거가 필요하다. 시각적 일치만으로 접근성을 입증하지 않는다.

### 기술 요구와 상세 설계

[TRD](../assets/templates/03-trd-architecture.md)는 언어·프레임워크 이름을 나열하기보다 선택 이유, 기존 제약, 구성 요소 경계, 데이터 흐름, 신뢰 경계, 실패 경로를 설명한다. 성능·가용성·복구·보안·비용 목표는 부하와 측정 환경을 포함한다. 임의의 “99.99%”나 “100ms”를 기본값으로 채우지 않는다.

[상세 설계](../assets/templates/04-solution-design.md)는 기능 하나가 어떤 상태와 순서로 완료되는지 적는다. 불변식, 트랜잭션 경계, 동시성, 중복 요청, 외부 실패 시 처리, 오류 후 회복을 다룬다. 중요한 선택은 [ADR](../assets/templates/09-decision-log.md)에 대안과 트레이드오프를 남긴다. 가벼운 함수 분해까지 ADR로 만들 필요는 없다.

### 계약과 데이터

[계약과 데이터](../assets/templates/05-contracts-data.md)에서 구현 전에 다음을 맞춘다.

- 요청·응답 스키마, 필수·선택·null의 의미, 타입·단위·길이·허용값
- 인증과 객체별 권한, 테넌트 경계, 서버 검증 책임
- 시간대, UTC 저장 여부, 날짜와 시각의 차이, 금액 통화와 최소 단위
- 안정적인 오류 코드와 사용자가 취할 다음 행동, 민감정보 비노출
- 타임아웃·취소·재시도 가능 오류·최대 시도·백오프와 총 대기 한도
- 멱등성 키의 범위·보관 기간·같은 키 다른 요청 처리·동시 요청 경합
- 데이터 키·고유 제약·참조 무결성·상태 전이·삭제·보존·백업
- 이벤트 중복·순서 바뀜·최종 일관성·재처리·실패 큐가 적용되는지
- 스키마·API 버전, 이전 클라이언트 호환, 단계적 마이그레이션

클라이언트 버튼 잠금만으로 중복 데이터나 권한 문제를 해결했다고 보지 않는다. 핵심 불변식은 서버·저장소에서도 보장하고 경쟁 조건을 실제로 시험한다. 모의 서버는 계약이 맞는지 조기 검토하는 수단이며 실제 저장·권한·트랜잭션 검증을 대신하지 않는다.

## 7 세로 기능 조각과 TDD 실행

[백로그](../assets/templates/07-backlog.md)는 계층별 긴 목록 대신 하나의 사용자 가치가 끝까지 이어지도록 나눈다. 예: 슬롯 선택 → 예약 요청 → 서버 검증·저장 → 완료 화면 → 새로고침 후 유지. 인증 같은 선행 작업은 명시적 의존성으로 둔다.

각 작업은 요구 ID, 인수 조건, 입출력, 담당자, 변경 파일, 선행 작업, 검증 방법, 허용 실행 범위, 완료·중단·재개 조건을 갖는다. 의존 관계를 DAG로 확인해 순환을 없앤다. 같은 파일·마이그레이션·공통 계약을 동시에 수정하지 않도록 소유자를 정하고 통합 담당자를 둔다. 병렬화는 파일이 다르다는 이유만으로 안전하지 않으며 공통 계약이 먼저 안정돼야 한다.

### 작업 시작 준비 조건

- 요구와 인수 조건이 식별되며 소유자가 정해졌다.
- 계약·데이터·권한·오류 의미가 작업에 충분히 명확하다.
- 중요한 미지수가 실험으로 해소됐거나 범위 밖으로 결정됐다.
- 테스트 환경·데이터·검증 방법이 있고 접근이 가능하다.
- 변경 파일과 의존성이 확인됐으며 충돌이 없다.
- 필요한 실행 권한과 비용 한도가 확인됐다.

### TDD 적용 루프

1. **Red**: 하나의 핵심 동작이나 결함을 재현하는 테스트를 먼저 작성한다. 직접 실행해 의도한 이유로 실패하는지 확인하고 결과를 남긴다. 의존성 설치 실패나 문법 오류는 요구를 검증하는 Red가 아니다.
2. **Green**: 테스트를 통과시키는 가장 작은 올바른 구현을 만든다. 정상 사례만 하드코딩하지 않고 명세의 경계를 지킨다. 대상 테스트와 영향받는 회귀 검사를 실행한다.
3. **Refactor**: 외부 계약을 유지하며 중복·복잡성을 정리하고 테스트를 다시 실행한다. 제품 범위를 추가하지 않는다.
4. **인수 검토**: 작성자가 아닌 관점에서 요구 충족, 테스트의 맹점, 실제 사용자 흐름을 확인한다. 별도 사람이 없으면 AI 검토 역할을 분리하되 독립 검토의 한계를 적는다.

TDD를 우선 적용할 곳은 계산, 규칙·권한 판단, 파서, 상태 전이, 멱등성, 회귀 버그, 핵심 데이터 불변식이다. 탐색 중인 UI·실험 코드는 작은 시제품을 먼저 만들 수 있지만, 재사용할 때 테스트와 인수 기준을 갖추고 검증한다. 비결정적 모델 응답은 정답 문자열 하나를 강제하는 단위 테스트만으로 다루지 않는다.

### 작업 완료 조건

코드 존재나 컴파일 성공만으로 완료하지 않는다. 관련 테스트, 계약 일치, 실제 저장·권한 경로, 사용자 인수 조건, 보안·성능 영향, 문서 변화, 증거 링크를 확인한다. 미검증 위험이 출시를 막는지 분류하고 `blocked` 또는 `deferred`로 기록한다. 전체 테스트를 실행할 수 없었다면 실행 범위와 미실행 범위를 분리한다.

## 8 검증을 설계하고 증거를 남기는 방법

[테스트 계획](../assets/templates/06-test-plan.md)에 요구별 테스트를 연결한다. 단계마다 다른 결함을 찾으므로 한 종류의 테스트를 늘려 모든 검증을 대체하지 않는다.

| 검사 | 확인할 내용 | 최소 증거 |
| --- | --- | --- |
| 정적 검사·빌드 | 타입·문법·의존성·산출물 생성 | 실제 명령, 환경·커밋, 종료 결과 |
| 단위 | 결정적 규칙, 경계값, 실패 분기 | 테스트 ID, 입력·기대값, 실제 결과 |
| 계약 | 클라이언트·서버·연동의 스키마와 오류 의미 | 계약 버전, 적합성 검사 결과 |
| 통합 | 실제 DB·인증·서비스 경계·경쟁 조건 | 사용 환경, 격리 데이터, 결과·정리 여부 |
| E2E | 사용자 관점의 시작부터 영속 결과까지 | 실제 브라우저·기기·백엔드, 단계·결과 |
| 시각·접근성 | 화면 상태, 반응형, 키보드·보조 기술 | 스크린샷, 크기, 검사 도구·수동 결과 |
| 비기능 | 성능·장애 회복·보안·개인정보·비용 | 부하·시간 창·설정·측정값·판정 |

E2E는 요청된 실제 사용자 경로를 끝까지 확인한다. 화면·API·저장이 범위인 경우 화면→API→실제 테스트 백엔드→데이터→재조회까지, 로컬 엔진/CLI는 입력→처리→출력/상태 및 필요한 재조회를 검증한다. 범위 밖 UI/API/원격 계층을 추가하지 않는다. 실제 사용자의 운영 데이터를 쓰지 않고 허가된 테스트 계정과 격리된 데이터를 사용한다. 외부 결제·메일 등은 승인된 sandbox를 우선하고 실제 발송·청구가 발생하는지 확인한다. 백엔드가 모의인 E2E는 그 사실을 표시하고 운영 경로 완료로 보고하지 않는다.

성능은 기기·지역·동시 사용자·데이터량·캐시·워밍업을 기록하고 p50·p95 등 목표에 맞는 수치를 측정한다. 보안은 권한 우회·다른 사용자의 객체 접근·입력 검증·비밀 유출·속도 제한을, 복구는 타임아웃·부분 실패·재시도·중복·백업 복원을, 비용은 대표 요청과 최악 사례의 사용량을 확인한다. 테스트 범위와 합격 기준은 위험에 비례해 정하며 무조건 100% 커버리지를 요구하지 않는다.

### AI 기능의 평가

AI를 써서 개발하는 것과 제품 안에 AI 기능이 있는 것은 구분한다. 제품에 비결정적 모델이 들어갈 때만 다음을 추가한다.

- 데이터 출처·동의·익명화·대표성을 점검하고 개발용 예시와 홀드아웃 평가 세트를 분리한다.
- golden set은 버전·출처·정답 또는 허용 범위·어려운 사례·안전 실패 사례를 갖춘다. 평가 정답을 프롬프트 튜닝·검색·학습 데이터에 섞지 않는다.
- 정확도·유용성·근거 충실도·거부 정확성·안전·지연·비용에 대해 관찰 가능한 rubric을 정의한다.
- 모델·프롬프트·도구·검색 데이터·온도·반복 횟수를 기록한다. 모델 심사만 믿지 않고 사람이 표본을 검토하며 심사 편향을 점검한다.
- 실패 유형과 치명적 실패 차단 기준을 별도로 둔다. 평균 점수가 좋아도 무단 실행·민감정보 노출 같은 치명적 오류는 통과시키지 않는다.
- 공급자·모델·프롬프트·검색 데이터가 바뀌면 회귀 평가한다. 비용·속도·품질을 함께 비교하고 폴백 또는 사람 확인 조건을 둔다.

### 증거의 최소 형식

`TEST ID / 커밋 또는 산출물 버전 / 실행 시각과 시간대 / 환경 / 명령 또는 수동 절차 / 기대 결과 / 실제 결과 / PASS·FAIL·NOT_RUN / 로그·스크린샷 위치 / 검증자`를 남긴다. 실패 로그의 토큰·개인정보를 가린다. 증거가 사라지지 않는 보관 위치와 기간을 정한다. 실제로 만들지 않은 경로나 URL은 링크하지 말고 `미생성`이라고 쓴다.

## 9 릴리스와 복구

[출시 런북](../assets/templates/08-release-runbook.md)에 환경별 담당자·릴리스 버전·명령·검증·중단 기준을 적는다. 개발·staging·운영의 설정과 자격 증명, 데이터, 외부 서비스 모드를 구분하고 운영에 가짜 데이터·디버그 설정이 넘어가지 않는지 확인한다.

출시 순서는 보통 **검증된 산출물 고정 → staging 배포 → 마이그레이션 리허설 → E2E·비기능 확인 → 출시 승인 → 제한된 노출 → 관측 → 확대**다. 실제 프로젝트에 적용하지 않는 단계는 이유를 남긴다.

데이터 변경은 백업이 있다는 선언으로 끝내지 않는다. 백업 시각·범위·복원 검증, 이전·새 코드의 호환 기간, 변경 전후 데이터 점검, 실패 시 중단 지점, 롤백 또는 롤포워드 가능성을 확인한다. 파괴적 마이그레이션은 되돌릴 수 없을 수 있으므로 실행 전 별도 승인과 복구 계획이 필요하다.

기능 플래그는 기본값, 대상, 켜고 끌 권한, 캐시·전파 지연, 해제 시 사용자 경험, 제거 계획을 정한다. 플래그를 끄는 것으로 데이터 변경이 되돌아가지는 않는다.

관측에는 핵심 사용자 성공률, 오류율, 지연, 비용, 큐·재시도, 데이터 무결성, AI 실패를 필요한 만큼 포함한다. 알림 임계값·수신 담당자·행동 절차를 정하고 한 번 확인한다. 로그는 상관 ID를 사용하되 비밀과 불필요한 개인정보를 남기지 않는다.

G4 통과는 **배포 가능한 상태**다. 실제 배포 권한과 실행 결과는 별도로 확인한다. 배포 뒤 smoke test와 실제 버전·대상 URL·데이터 상태를 검증하지 않고 출시 완료라고 하지 않는다.

## 10 출시 후 결과와 변경 관리

출시 직후 안정성 확인과 제품 성과 확인은 다른 시간 창을 가진다. 런북에 관찰 대상, 기간 또는 종료 조건, 담당자, 데이터 출처, 다음 결정을 적는다. “계속 지켜보기” 대신 **배포가 정상 상태에 도달했는지**, **정해진 기간에 목표 행동이 개선됐는지**를 확인한다. 실행 도구가 지속 작업을 지원하지 않으면 실제로 설정되지 않은 모니터링을 약속하지 않는다.

G5에서 성공·실패·근거 부족을 판단한다. 사용자 수가 적거나 측정이 고장났다면 성과를 확정하지 않는다. 기능이 배포됐어도 목표를 못 이뤘으면 가설·UX·범위를 재검토한다. 관찰이 완료되거나 사용자가 취소하거나 추가 권한이 필요하면 상태와 다음 책임자를 남기고 해당 작업을 끝낸다.

### 변경 요청 처리

1. 변경 이유·요청자·근거·기존 요구 ID·예상 효과를 기록한다.
2. 범위·UX·계약·데이터·보안·비용·일정·테스트·배포·복구 영향을 분석한다.
3. 제품·권한·비가역 영향이 있으면 결정권자에게 대안과 추천안을 제시한다.
4. 승인 또는 기술 위임 범위를 확인하고 기준 문서부터 갱신한다. 옛 가정을 폐기 표시하고 대체 ID를 연결한다.
5. 영향받는 작업과 테스트를 다시 준비 상태로 평가한다. 기존 PASS가 새 버전에 유효한지 판단한다.
6. 구현·회귀 검사·인수 검토·필요한 게이트를 다시 수행한다.

긴급 수정은 짧은 장애 기록으로 시작할 수 있지만, 원인·현재/기대 동작·유지할 동작·회귀 테스트·배포·복구 근거를 생략하지 않는다. 긴급 경로가 상시 품질 우회로가 되지 않도록 종료 후 문서를 정합화한다.

## 11 사람과 AI의 권한 및 협업

### 책임

사람은 제품 우선순위, 허용 위험, 비용, 개인정보·법적 판단, 공개 범위, 출시 승인을 책임진다. AI는 승인 범위 내 탐색·설계·구현·검증·문서 갱신을 맡는다. 기술 선택을 위임받아도 비용이나 보안 권한이 자동으로 넓어지지 않는다. 해당 플랫폼의 안전·승인 규칙이 이 문서보다 우선한다.

- 자격 증명은 안전한 입력·비밀 관리 절차로 공급한다. 채팅·문서·스크린샷에 비밀번호, API 키, 토큰을 요구하거나 저장하지 않는다.
- 비용은 공급자, 목적, 통화, 일회·반복 여부, 상한, 중단 조건을 정한다. 불명확하면 비용 발생 작업을 멈춘다.
- 삭제·덮어쓰기·마이그레이션은 대상·복원 가능성·영향 범위를 확인한다. 데이터 손실 위험을 일반적인 코드 수정 승인에 포함시키지 않는다.
- 공유·발송·공개는 정보와 수신자·권한을 지정한다. 테스트를 위해 외부로 보내는 데이터도 포함된다.
- 배포는 대상 환경·프로젝트·버전·공개 범위·비용·데이터 영향·복구 절차를 확인한다.
- 신규 설치·계정 생성·인증·영구 접근·결제에는 현재 도구가 요구하는 별도 승인이나 사용자 직접 단계가 필요할 수 있다.

### 승인된 범위 안에서 연속 진행

진행 범위는 단일 기능 또는 승인된 마일스톤으로 정한다. 마일스톤을 선택하면 기능 검증 뒤 의존성이 해소된 다음 작업을 계속하며 매번 진행 여부를 묻지 않는다. 게이트는 모든 기술 단계의 수동 승인 요구가 아니다. 목표의 완료 조건을 충족하거나 필수 승인·입력·접근·품질 문제가 남으면 멈춘다. 독립적인 준비 작업은 계속할 수 있다. 범위 확대와 배포는 별도 권한을 따른다.

### 여러 AI와 병렬 작업

작업을 맡길 때 목적·요구 ID·입력 링크·소유 파일·허용 변경·검증·보고 형식·중단·재개 조건을 전달한다. 하나의 공통 계약에 담당자를 두고 변경을 배포한 뒤 소비자가 따라가게 한다. 비밀 값을 인계하지 않는다.

진행 보고는 **완료한 결과 / 실제 검증 / 남은 위험 / 필요한 결정 / 다음 행동**만 짧게 남긴다. 작업량이나 추측으로 “90% 완료”라고 하지 않는다. 도구·접근·크레딧이 끊기면 사실을 알리고 증거와 현재 상태를 저장한다. 같은 실패를 무한히 반복하지 않고 원인을 분류해 대안을 제시한다. 재시도는 허용 권한, 비용, 실패 원인, 외부 부작용을 확인한 경우에만 한다.

[진행과 인계](../assets/templates/10-progress-handoff.md)에 현재 브랜치·커밋·미커밋 변경, 실행 중 프로세스, 문서 버전, 남은 작업, 실패 재현, 결정 대기, 다음 한 작업을 남긴다. 다음 AI는 이것을 읽고 현재 환경을 다시 확인한다. 과거 실행의 PASS를 현재 코드의 PASS로 복사하지 않는다.

## 부록 적용 범위와 단계 연결 기준

이 패키지의 파일 구조, 게이트, 승인표와 세부 템플릿은 드림피아 실무용 기준이다. 명세(Specify) → 계획(Plan) → 작업(Tasks) → 구현(Implement) → 검증·수렴(Converge)으로 이어지는 단계별 산출물과 요구·인수 조건·실행 작업을 일관되게 연결한다.

이 문서와 템플릿에 제시한 성능·비용·출시 판단 방법은 프로젝트별로 정해야 한다. 예시의 가상 요구와 데이터는 실제 서비스나 실제 실행 결과가 아니다.
