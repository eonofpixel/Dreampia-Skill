# 팀 작업 계약

목표 문서에는 사용자 의도·작은 작업·파일 소유권·검증 조건을 쓴다. 실행 상태와 증거는 목표 문서와 구별한다. 선택 하네스를 쓰면 `.harness/state.json` 및 `events.jsonl`을 사용하고, 쓰지 않으면 기존 프로젝트 진행 기록/증거 위치에 남긴다. 별도 원장이나 새 JSON 형식을 필수로 만들지 않는다. 목표 문서를 수정했다고 실행 완료가 되지 않는다.

기본은 단일 실행자다. 구현자와 검토자는 책임을 분리하고, 검토자는 근거와 실질 결함만 보고한다. 검토 수정은 변경 범위 및 영향을 받은 검증부터 수행한다. 최대 두 차례 검토 이후 남은 문제는 차단·실패·미실행으로 보고한다. 무한 수정 반복과 모델 자동 상향을 금지한다.

병렬 작업은 사용자가 허용한 독립 작업만 가능하다. 각 작업은 `owner`와 겹치지 않는 `owns` 상대 경로를 명시한다. 부모 디렉터리와 하위 경로도 겹침으로 판정한다. 하네스는 소유권 선언의 형태와 충돌을 검증하되 명령의 실제 파일 접근을 격리하지 않는다. 이번 하네스 엔진은 순차 실행한다.

각 작은 변경은 필요한 행동 회귀를 실패(Red)로 확인한 뒤 수정(Green)하고 완료 전 실제 검증을 수행한다. 낮은 영향의 문구 수정에 형식적인 테스트를 강요하지 않는다. 명령의 종료·현재 소스 해시·검증 명령 해시를 함께 확인한다. 실패·취소·차단·NOT_RUN을 완료라고 부르지 않는다.

재개 시 현재 목표와 증거를 대조한다. 외부 부작용 명령은 멱등성 책임을 작업자가 맡는다. 상태 복구 또는 manifest 변경 후 자동 replay하지 않고 명시적 부작용 승인으로만 재실행한다. exactly-once나 원격 실행 안전성을 보장하지 않는다.

긴 원시 출력은 상태나 이벤트에 복사하지 않는다. 이번 하네스는 기본적으로 stdout/stderr를 폐기하고 digest와 허용 메타데이터만 보관한다. 별도 상세 파일이 필요하면 작업자가 비밀을 제거한 명시적 프로젝트 파일로 작성하고 검증 입력에 연결한다.

승인 정책은 호스트가 담당한다. CLI 설치 승인은 `--apply`, provider 실행 승인은 `--allow-provider`, 부작용 replay는 `--accept-side-effects`다. 문서상의 역할 분리·TDD·검토 품질은 프롬프트 정책이며 프로그램이 의미상 준수를 인증하지 않는다. 입력 스키마·한정 재시도·증거 신선도·프로젝트 잠금·소유권 충돌은 코드로 검사한다.

사용자용 UI가 범위인 작업은 제품 화면·핵심 흐름·완료 기준부터 정하고 공통 스킬의 선택적 디자인 절차를 따른다. 목업·내부 런타임 PoC·연결된 UI·합의된 제품 완료를 구별한다. 화면을 못 봤으면 시각 검증은 NOT_RUN이다. backend/CLI-only에는 UI를 요구하지 않는다. 디자인 판단·실제 화면 품질은 프롬프트 계약이며 하네스 자동 검사 대상이 아니다.
